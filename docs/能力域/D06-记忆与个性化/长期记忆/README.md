## 长期记忆去重与更新

### 问题与目标

同一用户在持续对话中，“英语初学者”“正在做造句练习”“语法较弱”等事实被反复换词提取。原有 pg_trgm 阈值去重不能可靠识别语义重复，命中后直接覆盖又可能丢失“使用扇贝”等有效细节。练习题号、当前作业与稳定画像混在 L2 中，使长期记忆不断膨胀。

目标是维护可复用的独立事实，减少重复，同时保留补充信息和明确变化。相同话题不等于同一事实，不以最少条数作为合并目标。

### 本次交付范围

1. 后台自动提取和 Agent 的 `memory_write` 共用 `reconcile_memory`。
2. L1/L2 使用完全重复检查、候选召回和模型事实判定。L3 保留原有文本去重与每日摘要链路。
3. 更新记忆提取与工具提示，区分长期事实和临时状态。
4. 后端保留最近 10 次合并/更新前的内容、时间、来源；当前页面无需新增控件。
5. 不自动批量重写已有数据。手动新增、编辑和 `/remember` 保持既有语义。

### 事实分类

| 内容 | 保存方式 |
|---|---|
| 初学者、语法较弱、使用扇贝背单词 | 同一学习画像事实，补充合并 |
| 中文出题、用户翻译、逐条纠错、逐步加难 | 独立练习偏好 |
| 回复先翻译用户消息 | 独立回复规则 |
| 只负责英语教学，不主动介入其他话题 | 独立角色边界 |
| 当前第 3 题、今日作业、单次纠错 | L3 情景摘要及每日记忆 |

每条新记忆描述一个独立事实。只提取用户明确表达或对话确认的信息，不能把助手建议自动当成用户偏好。分类由提取和工具提示约束，后端不使用关键词硬编码推断用户意图。

### 写入决策

| 决策 | 条件 | 行为 |
|---|---|---|
| skip | 已有事实完整包含本次信息 | 保留 ID 和正文，合并标签与来源 |
| merge | 同一事实新增互补细节 | 保留 ID，保存包含双方有效细节的完整正文，记录旧版本 |
| update | 同一事实被明确修正或改变 | 保留 ID，替换已改变部分、保留其他细节，记录旧版本 |
| create | 独立新事实、关系不确定或判定失败 | 新增，不能仅因文字相似覆盖旧事实 |

模型只能引用候选 ID。跨用户、跨智能体、跨层级的目标均视为非法，不进行修改。冲突内容如果缺乏可靠的变化证据，应新增而不是认定最后写入的一定正确。

### 实现约束

- 提取前加载当前作用域最近 40 条 L1/L2，提示模型不重复提取已知事实，每轮最多写入 5 条 L2。
- 写入时重新查询数据库，不信任提取阶段快照；候选为同作用域、同层级的文字相关性前 12 条与最近更新 12 条的并集（最多 24 条）。不跨智能体共享范围合并。
- 完全相同的去首尾空白正文直接复用，不调用模型。没有候选时直接新增。
- 其余 L1/L2 写入使用用户租户默认模型判定，调用上限 12 秒。错误或非法结构降级新增，旧正文不变；日志只记录错误类型。
- 同用户、智能体、层级使用 PostgreSQL 事务 advisory lock，覆盖候选查询、模型判定和数据库写入；等待上限 20 秒，超时失败，不绕过锁插入。
- 自动提取逐条提交并释放锁，每条提交后下一条重新设置 RLS 上下文。后续条目失败不会回滚已成功保存的条目。
- 工具超时元数据调整为 45 秒；服务本身通过显式超时限制锁等待和模型调用。
- revisions 元数据最多保存最近 10 次旧正文、旧 updated_at、旧 source_session 和修改动作；不提供无限历史或 UI 回滚。
- 手工创建路径不使用此锁/判定，不保证它与自动写入之间的全局去重。

### 验收

- 相同事实重复写入：只保留一条，合并来源，不调用判定模型。
- 换词表达且模型判定重复：复用原 ID，不改旧正文。
- 补充语法弱点时，合并结果保留原来的扇贝 App 信息；旧正文可在 revisions 查到。
- 用户明确改变某事实时，更新原条目并保留最近旧版本。
- 画像和回复规则虽都与英语相关，独立事实判定为新增。
- 非法 JSON、无效动作、空合并正文、超时、伪造/越权 ID 均不能覆盖旧数据。
- 不把其他用户、其他智能体或其他层级的条目发送给判定模型。
- 两个并发自动写入在空作用域写入相同事实，只产生一条。
- 自动提取和工具调用都使用新服务，原 L3/每日记忆及作用域测试通过。

### 已知限制与后续需求

模型语义判断仍可能出错；有限候选召回无法保证找到所有历史同义事实。模型不可用时优先保留信息，可能产生重复。临时进度分类是模型提示约束，不是独立的确定性状态存储。

本次防止后续自动写入继续简单追加，不进行存量批量清理。后续“整理记忆”应先生成旧条目到新事实的合并预览，展示被保留和替换的信息，再执行可追溯的整理；当前版本尚未实现该入口。跨会话唯一最新学习进度、来源事件排序和完整版本回滚也不属于本次交付。

## 长期记忆整理与纠错

### 用户流程

在「记忆管理」选择用户共享或某个智能体的专属记忆，再选择长期记忆（L2）或常驻上下文（L1）。点击「整理记忆」，或勾选 2–30 条后点击「整理所选」。

1. **整理预览**：并排显示原始正文、来源会话 ID、合并理由与合并后的正文；可以先人工纠正建议。预览只保存建议，不改变任何记忆。
2. **确认合并**：默认不勾选建议；用户勾选需要的组并确认后才写入。保留目标记忆 ID，汇总标签和来源，被合并的原始条目在版本账本中保留完整快照。
3. **来源与版本**：每条记忆可查看历次正文、层级、范围、元数据及修改时间。来源会话通过所有权校验后显示标题和可点击链接；已删除、不属于当前用户或聊天室来源只保留原 ID。
4. **纠错**：编辑记忆生成新版本。可以恢复任一完整历史版本的正文、层级、所属智能体和元数据；恢复本身同样生成新版本。
5. **修改记录与撤销**：可以撤销合并、人工纠错、自动更新、创建、删除或批量删除。撤销合并恢复整组原始 ID、正文、来源、标签和其他元数据，不只是恢复一段文本。已合并或删除的条目应从修改记录撤销整次操作，不能单独恢复一个已删除版本。

每日记忆（DailyMemory）仍使用原有时间线，不包含在本次整理中。L3 条目的普通 CRUD 也会留存版本，但不提供整理入口。

### 整理与冲突规则

- 查询和确认严格限定当前用户、同一 agent_id（含用户共享）与同一层级，不能跨范围合并。
- 自动预览每批最多 200 条，提供下一批入口。先合并正文完全相同的条目；从其余条目按文本相似度挑选最多 30 个候选交给模型提出语义建议。不同批次不自动交叉比较，可以搜索并手动选择相关条目后整理。
- 模型只能提出建议，不能执行修改；只接受候选内、互不重叠、至少包含两个 ID 的分组。提示词要求保留事实、时间与限定条件，矛盾事实保持分开。
- 模型调用最多等待 20 秒，输入正文总量最多 60000 字。模型不可用或输出不合法时，保留确定的完全重复建议；手动选择的条目退回原文拼接并明确提示人工核对，不静默生成猜测内容。
- 合并正文最多 5000 字，超长原文无法拼接时提示减少选择。模型返回无可合并建议时不会强制合并。
- 预览保存在服务端，有效期一小时。确认时锁定记录并比较完整原始快照和版本；正文、元数据、来源、层级、范围、删除状态任一变化都返回 HTTP 409，整个请求不执行部分合并。
- 同一预览、同一确认内容重复提交返回原操作凭据；不同内容重复提交被拒绝。同一次撤销重复请求也返回原撤销凭据。
- 编辑和恢复使用期望版本；ORM 更新/删除同时执行版本校验。撤销检查所有关联记忆最新版本和删除快照：任何后续修改都会阻止覆盖，即使正文后来又改回原样。
- PostgreSQL advisory lock 沿用自动记忆整理的用户、智能体与层级维度，并配合行锁处理确认与撤销。SQLite 单元测试不覆盖 PostgreSQL 锁或 RLS 行为。

### 数据与接口

新增 `Memory.version` 和三张表：

| 表 | 用途 |
| --- | --- |
| `memory_versions` | 按记忆 ID 和递增版本存完整快照；删除也写入快照 |
| `memory_changes` | 保存一次操作涉及的所有记忆修改前后状态和撤销凭据 |
| `memory_organize_plans` | 保存服务端预览、原始版本、确认摘要和操作凭据 |

新增表包含用户所有权过滤与 PostgreSQL RLS。自动提取中的更新、合并、仅补充来源，以及普通 CRUD 均接入版本记录。完整版本存储不再受旧 `metadata.revisions` 最多 10 条的限制。

| 方法 | 路径（前缀 `/api/memories`） | 用途 |
| --- | --- | --- |
| POST | `/organize/preview` | 创建预览，参数 layer、agent_id、可选 ids/offset |
| POST | `/organize/{plan_id}/apply` | 确认选中组和人工核对后的正文 |
| GET | `/changes` | 按范围、层级、offset 分页查询修改记录 |
| POST | `/changes/{change_id}/undo` | 原子撤销一次操作 |
| GET | `/{memory_id}/versions` | 版本、可访问的来源会话、旧正文记录 |
| POST | `/{memory_id}/versions/{version}/restore` | 恢复完整版本，必传 expected_version |

现有更新接口增加可选 `expected_version`，前端始终传递；列表和搜索响应包含 version、metadata 和更新时间，搜索结果不再丢弃来源元数据。
