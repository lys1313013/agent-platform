# 运行模式（Ask / Plan / Agent）— 设计

> 需求见 [需求](01-需求.md)。本文定义模式与全自动档的数据模型、执行流程、策略优先级、计划审批与失败处理。

## 1. 设计原则

1. **服务端强制**：模式与执行档由服务端校验并执行，客户端字段只作为输入，不作为权限依据。
2. **模式是上限，不是放行**：Ask/Plan 把工具能力压到只读；Agent 不放宽任何现有权限与确认策略；全自动只跳过确认，不把拒绝变允许。
3. **批准绑定内容**：用户批准的是某一份计划，不是“允许这个任务随便做”。
4. **零副作用可验证**：Plan 批准前、Ask 全程，不产生文件、消息、命令或外部写操作。
5. **可恢复**：模式、计划、批准与切换记录持久化，进程重启和断线重连后状态不丢。

## 2. 数据模型

### 2.1 运行模式

在运行任务上增加模式字段，随任务创建写入：

```
chat_runs.mode            -- ask | plan | agent
chat_runs.auto_profile    -- interactive | auto（仅 agent 模式有效）
chat_runs.auto_policy     -- JSONB：工具白名单、限额、不可自动执行清单快照
chat_runs.plan_id         -- 当前生效计划（plan 模式）
chat_runs.mode_locked_at  -- 模式最后一次显式变更时间
```

会话级默认模式可存放在 `sessions` 或用户配置中；任务创建时复制为任务模式，之后不随会话默认值变化。

### 2.2 计划

```
run_plans
  id, tenant_id, user_id, session_id, run_id
  version              -- 同一 run 内递增
  status               -- draft | pending | approved | rejected | superseded | expired
  goal                 -- 目标
  steps                -- JSONB：步骤列表
  assumptions          -- 假设与前置条件
  risks                -- 风险与需要确认的点
  expected_artifacts   -- 预期产物
  estimated_tokens     -- 可选：预估成本
  digest               -- 规范化内容的哈希，用于绑定批准
  created_at, created_by
  approved_at, approved_by
  rejected_at, rejected_by, reject_reason
  expires_at
```

步骤结构建议：

```json
{
  "id": "s1",
  "title": "读取现有配置",
  "description": "读取工作区中的配置文件并确认字段",
  "tools": ["read_file"],
  "side_effects": false,
  "risk": "low",
  "expected_output": "配置字段清单"
}
```

`side_effects=true` 的步骤在 Plan 批准前不得执行；批准后仍受动作级确认策略约束。

### 2.3 模式切换记录

```
run_mode_transitions
  id, run_id, tenant_id, user_id
  from_mode, to_mode
  reason, actor_type, actor_id
  created_at
```

## 3. 策略优先级

实际可用能力取三层交集：

```
effective = mode_ceiling ∩ tool_permission ∩ trust_level ∩ execution_profile
```

- `mode_ceiling`：
  - ask：只读工具（检索、读取、查询），禁止写入、执行、对外发送、创建任务。
  - plan：与 ask 相同，额外允许生成计划文本。
  - agent：不额外收紧。
- `tool_permission`：现有只读/写入/危险分级。
- `trust_level`：现有总是询问/仅危险询问/全部自动。
- **模式优先于信任级别**：即使 `trust_level=auto_all`，ask/plan 也不能产生副作用。
- **Agent 模式不提升权限**：危险动作仍按策略确认；配额、租户、确认、审计照常生效。
- **全自动档只影响确认，不影响拒绝**：`trust_level` 与 `auto_profile` 只能把“需要确认”降为“直接执行”，不能覆盖策略拒绝、权限、配额、租户隔离与审计。

### 3.1 副作用判定

工具是否属于副作用，按以下顺序判定：

1. 工具注册的权限级别为 `write` 或 `dangerous` → 副作用。
2. 远程工具方法不是 GET/HEAD/OPTIONS → 副作用。
3. MCP 工具默认按副作用处理，除非显式声明只读。
4. 直接处理器（记忆写入、技能创建、定时任务、委派等）按注册的权限级别判定。
5. 未知工具 → 按副作用处理（失败关闭）。

## 4. 执行流程

### 4.1 创建任务

1. 请求携带 `mode`；未携带时取会话默认值。
2. 服务端校验模式合法性与调用者权限，写入 `chat_runs.mode`。
3. 绑定执行租户、智能体与会话，后续不读取界面当前租户。
4. 返回任务标识与模式，前端据此渲染。

### 4.2 Ask 模式

1. 构造工具列表时只保留只读工具。
2. 执行器对写入/危险工具再次拒绝，防止绕过工具列表。
3. 不创建后台副作用任务，不写入记忆/技能/定时任务。
4. 若模型坚持调用被禁工具，返回结构化错误，让模型改用只读方式回答。
5. 用户要求执行动作时，提示切换到 Plan 或 Agent，不静默降级。

### 4.3 Plan 模式

1. 以只读工具做必要调研。
2. 模型输出结构化计划，服务端按 schema 校验并持久化为 `draft`。
3. 计划完整后置为 `pending`，计算 `digest`，向客户端推送 `plan_required`。
4. 阻塞等待批准；等待可跨请求生命周期，状态持久化。
5. 用户操作：
   - 批准：校验 `digest` 与计划版本，置为 `approved`，任务模式切换为 `agent`，进入执行。
   - 拒绝：置为 `rejected`，任务停留或结束，不执行任何步骤。
   - 修改：生成新版本 `draft`，旧版本 `superseded`，重新走审批。
6. 计划过期：超过 TTL 置为 `expired`，默认按拒绝处理（失败关闭）。
7. 执行阶段把已批准计划作为附加上下文注入，但不得因“已批准”跳过工具级确认。

### 4.4 Agent 模式

保持现有执行路径：工具权限、确认策略、并发、配额、审计不变。子智能体继承 Agent 模式。

### 4.5 Agent 全自动档

全自动不是独立模式，而是 `mode=agent` 上的执行档 `auto_profile=auto`。它改变的是确认环节，不改变权限与数据边界。

#### 4.5.1 决策模型

对每次工具调用，按以下顺序求值：

```
1. 租户隔离 / 资源权限 / 配额 / 审计   → 不满足则 deny（全自动不可覆盖）
2. 不可自动执行清单                 → 命中则 deny
3. 工具是否在白名单                 → 不在则按交互策略处理
4. 工具风险与 auto_policy           → allow | confirm
5. 交互档时 confirm 走确认；全自动档 confirm 直接 allow
```

**关键约束**：全自动只能把第 5 步的 `confirm` 变为 `allow`；第 1、2 步的 `deny` 始终生效。

#### 4.5.2 不可自动执行清单

默认包含：

- 支付、转账、下单、退款。
- 导出凭证、密钥、Cookie、会话令牌。
- 批量删除或批量停用。
- 向新收件人外发消息/邮件。
- 租户、成员、角色、配额、白名单等平台配置变更。
- 安全策略判定为高风险且未显式加入白名单的动作。

租户管理员可调整清单；调整本身进入审计。

#### 4.5.3 限额与停止条件

`auto_policy` 至少包含：

```
max_steps, max_tokens, max_cost, max_wall_seconds,
max_consecutive_failures, max_repeated_calls,
allowed_tools, denied_actions
```

命中任一条件时：

1. 停止调度新的工具调用。
2. 在途调用按取消策略处理，结果如实记录。
3. 任务进入 `stopped` 终态，附停止原因、已完成动作、已产生副作用、未执行步骤。
4. **不静默降级为交互模式继续跑**；是否继续由用户显式决定。

#### 4.5.4 事后复盘

- 任务结束后生成执行摘要：动作列表、资源变更、费用、被拦截动作、停止原因。
- 摘要进入审计与任务详情，用户可标记问题；标记结果可用于收紧白名单或关闭全自动。

### 4.6 子智能体

- 子任务创建时继承父任务模式与执行档，不允许高于父级。
- 父任务为 Ask/Plan 时，子任务同样受只读限制。
- 父任务为 Agent 时，子任务仍受自身工具白名单与权限限制；父任务为全自动时，子任务继承全自动但同样受限额与不可自动执行清单约束。

## 5. 模式切换

### 5.1 状态机

```
ask  --用户--> plan
ask  --用户--> agent
plan --用户--> ask
plan --批准--> agent
agent --用户--> plan
agent --用户--> ask
```

**禁止**：plan → agent 未经批准；任何模式自动降级为 Agent；子任务提升父级模式。

### 5.2 切换语义

- **Ask → Plan/Agent**：立即生效，下一轮工具列表按新模式构造。
- **Plan → Agent**：必须存在 `approved` 且 `digest` 匹配的计划；否则拒绝。
- **Agent → Plan/Ask**：
  - 停止调度新的副作用动作；
  - 在途工具调用按现有取消策略处理（可完成或取消，结果如实记录）；
  - 已完成的写入不回滚，向用户明确说明；
  - 记录切换原因。
- 每次切换写入 `run_mode_transitions`，并推送 `mode_changed` 事件。

## 6. 接口与事件

### 6.1 请求

- 创建任务/会话的请求增加 `mode` 字段（`ask | plan | agent`）与 `auto` 布尔字段（仅 Agent 有效）。
- 开放 API 必须显式支持；未指定时使用会话默认值。
- 模式切换使用独立端点，不能通过修改历史消息间接改模式。

### 6.2 流式事件

| 事件 | 说明 |
|---|---|
| `run_mode` | 任务当前模式 |
| `plan_required` | 计划待批准，携带计划内容、版本、摘要 |
| `plan_status` | 批准/拒绝/过期/被新版本取代 |
| `mode_changed` | 模式切换，含原模式、新模式、原因 |
| `mode_violation` | 模型尝试调用副作用工具被拒绝 |
| `auto_policy_applied` | 全自动档生效，携带白名单与限额 |
| `auto_stopped` | 全自动因限额、失败、命中清单或用户停止而终止 |

### 6.3 渠道降级

- 渠道支持 Ask / Agent。
- Plan 需要可交互审批：支持按钮或命令的渠道可保留 Plan；否则在任务开始前明确提示“当前渠道不支持计划审批”，由用户选择 Ask 或 Agent，不静默按 Agent 执行。

## 7. 失败处理

| 场景 | 处理 |
|---|---|
| 计划生成失败 | 停留在 Plan，返回错误；不执行任何步骤 |
| 计划 schema 非法 | 拒绝持久化，要求重新生成；记录失败原因 |
| 批准丢失/进程重启 | 计划与批准状态已持久化，恢复后继续等待或按已批准执行 |
| 批准后计划被修改 | `digest` 不匹配，批准失效，必须重新批准 |
| 模式切换时工具在途 | 记录真实结果，不伪造成功；已完成的副作用如实告知 |
| 客户端伪造模式/执行档 | 服务端以持久化模式与执行档为准，忽略不一致输入 |
| 全自动命中断言/限额 | 停止并进入明确终态，不静默转交互继续 |
| 全自动遇到不可自动执行动作 | 拒绝该动作并记录；任务可按策略停止或继续其余步骤 |
| 计划过期 | 默认拒绝，不自动执行 |

## 8. 可观测与审计

- 审计事件：模式与执行档选择、计划创建/修改/批准/拒绝/过期、模式切换、副作用工具被拒绝、全自动拦截与停止。
- 指标：各模式任务数、计划批准率、从计划到执行的时间、Plan 模式下的只读工具调用量、模式违规次数、全自动任务占比/停止率/平均费用。
- 计划与切换记录保留期与审计策略一致，支持按任务回溯。

## 9. 测试建议

- Ask：写入、执行、外发、创建任务全部被拒绝；只读工具正常。
- Plan：批准前零副作用；批准后可执行；修改计划导致批准失效；拒绝与过期不执行。
- Agent：现有工具权限与确认行为不回归。
- 全自动：常规确认被跳过；租户、权限、配额、审计仍生效；不可自动执行清单命中即拒绝；限额触发即停止。
- 切换：Agent→Plan 停止新副作用；Plan→Agent 必须有批准；子智能体不能提升模式。
- 恢复：进程重启、断线重连后模式与计划状态一致。
- 渠道：不支持 Plan 时明确降级，不静默执行。
