# 运行模式（Ask / Plan / Agent）— 需求

> 让用户在发起任务前明确选择智能体的自主程度：只回答、先出计划再执行、或直接执行；Agent 可进一步选择全自动档。本文定义任务级模式；动作级审批与信任级别仍由安全策略负责。

## 1. 背景与问题

当前平台只有**动作级**控制：工具权限分只读/写入/危险，信任级别分总是询问/仅危险询问/全部自动。它能回答“这个工具要不要确认”，但不能回答用户更关心的问题：

- 我现在只想知道答案，不希望智能体动任何文件。
- 这个任务比较复杂，我想先看它打算怎么做，再决定是否执行。
- 我已经明确要它做完，不要再逐步问我。

缺少任务级模式带来三个问题：用户无法预判智能体会不会产生副作用；复杂任务直接开跑，返工成本高；同一套确认策略无法同时满足“问答”和“自动执行”两类场景。

## 2. 目标

- 提供三档任务级模式：Ask（只读问答）、Plan（先计划、批准后执行）、Agent（直接执行）。
- 模式在任务开始时确定，并贯穿整个执行过程；切换必须显式、可审计。
- Plan 模式在用户批准计划前不产生任何副作用。
- Ask 模式禁止写入、执行命令、对外发送等副作用动作。
- Agent 模式沿用现有工具权限与确认策略，模式不放宽安全边界。
- Agent 提供“全自动档”：跳过交互确认，但不能绕过租户、权限、配额、审计与不可自动执行的高危动作。

## 3. 范围

**纳入**：
- Web 管理端、用户门户、开放 API 的模式选择与传递。
- 会话/任务级模式持久化与恢复。
- Plan 模式下的计划生成、展示、批准、拒绝、修改后重新批准。
- Ask 模式下的工具白名单与副作用阻断。
- 模式切换规则、事件与审计记录。
- Agent 全自动档的范围、限额、停止条件与事后复盘。
- 渠道场景的降级方案。

**不纳入**：
- 替代动作级审批与信任级别。
- 多智能体自动规划、工作流编排器。
- 计划执行过程中的逐步审批（首期按整份计划批准）。
- 对已完成副作用的自动回滚。

## 4. 功能需求

### 4.1 模式定义

| 模式 | 允许行为 | 禁止行为 |
|---|---|---|
| Ask | 回答、检索、读取用户有权访问的资料 | 写文件、执行命令、调用外部写接口、创建任务、对外发送 |
| Plan | 只读调研、生成计划、等待批准 | 批准前的任何副作用动作 |
| Agent | 在工具权限与确认策略内自主执行；可开启全自动档 | 绕过租户、权限、配额与审计约束 |

### 4.2 模式选择与持久化

- 新建任务/会话时可选择模式；默认模式由平台或用户配置决定。
- 模式随会话/任务保存，刷新、重连、后台恢复后保持一致。
- Agent 模式还需选择执行档：交互（逐次确认）或全自动（跳过可跳过的确认）。
- 开放 API 请求必须能显式指定模式与执行档；未指定时使用会话默认值。
- 渠道场景默认 Ask 或 Agent；Plan 需要可交互审批载体，不支持时降级并明确告知。

### 4.3 Plan 模式

- 计划至少包含：目标、步骤、将使用的工具/外部系统、预期产物、风险与需要用户确认的点。
- 计划生成只允许只读调研；不得提前创建文件、发消息、执行命令。
- 用户可批准、拒绝或要求修改；拒绝后回到规划，不执行。
- 批准绑定计划版本：计划内容或步骤发生变化，原批准失效，必须重新批准。
- 批准后进入执行，执行阶段仍受动作级确认策略约束。
- 计划与批准结果需要持久化，支持事后查看。

### 4.4 Ask 模式

- 只允许只读工具与检索；写入、执行、对外发送类工具直接拒绝并返回明确原因。
- 不得因为信任级别为“全部自动”而放宽 Ask 限制；模式优先于信任级别。
- 用户要求执行副作用动作时，提示切换到 Plan 或 Agent，不静默降级。

### 4.5 Agent 模式

- 保持现有行为：工具权限、确认策略、配额与审计共同约束。
- 危险动作仍按策略确认，模式不构成“全部放行”。
- 子智能体继承父任务的模式；子任务不得提升模式。

### 4.6 Agent 全自动档

全自动不是第四种模式，而是 Agent 的执行档：任务仍是 Agent，内部用“Agent + 全自动”表达。

**允许跳过**：
- 常规写入、文件修改、沙箱命令、普通外部 HTTP 写操作等可配置的确认。
- 重复性确认：同一计划内已批准过的同类操作不重复询问。

**不得跳过**：
- 租户隔离、资源权限、配额、审计与速率限制。
- 不可自动执行清单：支付/转账、导出凭证或密钥、批量删除、向新收件人外发、租户与权限配置变更。该清单由租户管理员维护，默认全部禁止自动执行。
- 安全策略判定为拒绝（deny）的动作；全自动只能跳过“需要确认”，不能把“拒绝”变成“允许”。

**必须配置的护栏**：
- 最大步数、最大 token/费用、最大墙钟时间。
- 工具白名单；未在白名单内的工具仍按交互策略处理或拒绝。
- 循环检测与连续失败阈值；命中即停止，不继续烧预算。

**停止条件**：
- 达到步数、费用、时间上限。
- 连续失败、重复调用、异常输出。
- 命中不可自动执行动作。
- 用户主动停止或权限被撤销。

停止后进入明确终态，保留已完成动作、已产生副作用与未执行步骤的清单，不静默降级为交互模式继续跑。

**事后复盘**：
- 全自动任务结束后生成执行摘要：做了什么、改了哪些资源、花了多少、哪些动作被策略拦截。
- 用户可在任务详情中逐项查看并标记问题，用于后续收紧白名单或关闭全自动。

### 4.7 模式切换

- Ask → Plan / Agent、Plan → Agent：允许，由用户显式触发。
- Agent → Plan / Ask：立即停止调度新的副作用动作；在途动作按取消策略处理；已完成的写入不回滚，并向用户说明。
- Plan → Agent 必须经过计划批准；未批准不得切换执行。
- 任何切换记录时间、操作者、原模式、新模式与原因。

### 4.8 事件与展示

- 前端需要收到模式状态、计划内容、等待批准、批准/拒绝结果与模式切换事件。
- 计划展示应能区分“待批准”“执行中”“已完成”“已拒绝”。
- 后台任务与断线重连后，模式与计划状态可恢复。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 安全 | Plan 批准前、Ask 全程零副作用；全自动只能跳过确认，不能绕过权限、租户、配额、审计与不可自动执行清单 |
| 一致性 | 同一任务在 Web、API、渠道看到同一模式与计划状态 |
| 可审计 | 模式与执行档选择、计划版本、批准人、批准时间、切换记录、全自动拦截与停止原因可查询 |
| 可恢复 | 进程重启或断线后，模式与计划状态不丢失 |
| 兼容性 | 不改变现有 Agent 模式下的工具与确认行为 |

## 6. 验收标准

- [ ] 新建任务可选择 Ask / Plan / Agent，刷新与重连后模式不变。
- [ ] Ask 模式下写文件、执行命令、对外发送均被拒绝，并返回可理解原因。
- [ ] Plan 模式下未批准计划前，不产生任何文件、消息、命令或外部写操作。
- [ ] 用户可以批准、拒绝、要求修改计划；拒绝后不执行。
- [ ] 计划内容变更后，原批准失效，必须重新批准。
- [ ] Agent 模式下现有工具权限与确认策略行为不变。
- [ ] Agent 切换到 Plan 后不再发起新的副作用动作，已完成的写入有明确说明。
- [ ] Agent 全自动档可跳过常规确认，但租户、权限、配额、审计仍然生效。
- [ ] 全自动档命中不可自动执行清单时拒绝执行，并记录原因。
- [ ] 全自动达到步数、费用、时间或连续失败阈值时停止，进入明确终态。
- [ ] 子智能体继承父任务模式与执行档，不能自行提升。
- [ ] 模式、计划版本、批准与切换记录可查询、可审计。
- [ ] 渠道不支持 Plan 交互时，有明确降级提示，不静默按 Agent 执行。
