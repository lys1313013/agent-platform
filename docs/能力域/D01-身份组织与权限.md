# D01 身份、组织与权限

> **解决什么问题**：谁能进入平台、属于哪个组织、能看到和操作哪些资源。
> **适用读者**：后端、前端、安全评审、交付实施。
> **关联文档**：[D10 安全合规与审计](D10-安全合规与审计.md) · [D12 成本与配额](D12-成本与配额.md) · [能力全景 §5 D1](../企业级Agentic平台能力全景.md)
> **状态基准**：2026-11 代码。状态用 `已具备 / 部分 / 缺失`。

---

## 1. 边界

**本文负责**：
- 组织模型：租户、部门/项目、用户、成员关系。
- 认证：账号密码、会话、SSO、MFA、服务身份。
- 授权：角色、资源可见性、资源级 ACL、数据行级权限。
- 生命周期：注册、邀请、加入/退出、停用、离职、租户切换。

**本文不负责**：
- 操作留痕与合规取证 → D10。
- 用量计量与配额 → D12。
- 智能体内部的工具白名单与子智能体权限继承 → D04 / D07。

**设计底线**：任何资源都必须能回答三个问题——**属于谁（租户/用户）**、**谁能看（可见性）**、**谁能改（角色/ACL）**。三者缺一，隔离就不成立。

## 2. 能力清单

### 2.1 组织模型

| 层级 | 作用 | 最低要求 |
|---|---|---|
| 平台 | 跨租户运营、模型供应商、系统配置 | 超级管理员 |
| 租户 | 数据隔离与计费单元 | 必须有 |
| 部门/项目 | 资源归属与权限分组 | 企业版建议有 |
| 用户 | 身份主体 | 必须有 |
| 服务账号 | 机器调用主体 | 对外 API 必需 |

**决策点**：
- 用户是否允许属于多个租户？允许时，必须有"当前活动租户"和"执行租户"两个概念，且后台任务不能用 UI 当前租户推断。
- 部门是资源归属维度还是权限维度？建议两者都是：资源挂部门，权限按部门授予。
- 租户之间是否允许共享资源？默认禁止；需要共享时走显式发布/订阅，不做隐式可见。

### 2.2 认证

| 能力 | 企业要求 | 说明 |
|---|---|---|
| 账号密码 | 必须 | 密码策略、bcrypt/argon2、失败锁定 |
| 访问令牌 | 必须 | 短期 JWT，含用户与角色 |
| 刷新令牌 | 必须 | 哈希存储、轮转、可吊销 |
| SSO | 企业采购硬门槛 | OIDC / SAML / CAS，至少一种 |
| 目录同步 | 中大型企业 | LDAP/AD 或 SCIM |
| MFA | 安全评审常见要求 | TOTP / 企业 MFA |
| 服务身份 | 开放平台必需 | API Key / OAuth Client Credentials |
| 会话管理 | 建议 | 查看登录设备、主动下线 |

**令牌设计要点**：
- access token 短（15 分钟级），refresh token 长但必须可吊销、可轮转。
- refresh token 轮转后旧 token 立即失效，防止重放。
- 用户停用后，refresh 流程必须拒绝；access token 在过期前仍有窗口，需在关键操作上二次校验用户状态（当前实现每次请求都查 `User.is_active`）。
- 角色变更后旧 access token 仍携带旧角色，敏感操作应以数据库角色为准，不能只信 token 里的 `role`。

### 2.3 授权

建议采用四层判定，顺序不可颠倒：

```
1. 租户边界：资源 tenant_id == 当前执行租户
2. 资源可见性：tenant（租户内公开） / private（仅创建者或授权者）
3. 角色：superadmin / tenant_admin / member / viewer
4. 资源 ACL：显式授予某用户/部门某操作（read/write/admin）
```

**权限点建议**：
- 平台级：租户管理、模型供应商、系统配置、全局审计。
- 租户级：成员管理、智能体发布、知识库管理、渠道配置、工具/MCP 管理、配额查看。
- 资源级：查看、编辑、删除、发布、调用、授权他人。
- 数据级：知识库文档、会话、记忆、产物的访问。

**禁止的做法**：
- 只靠前端隐藏按钮。
- 只靠 JWT 里的 role，不查数据库。
- 先检索再按权限过滤（会泄露存在性与数量）；必须在查询条件里过滤。
- 用 `visibility=tenant` 代替 ACL 表达"某部门可见"。

### 2.4 资源归属与可见性

| 资源 | 归属 | 建议可见性 |
|---|---|---|
| 智能体 | 租户 | tenant / private / 指定成员 |
| 知识库、图谱 | 租户 | tenant / private |
| MCP Server、远程工具 | 租户 | tenant |
| 渠道配置 | 租户 | 管理员可见 |
| 会话、消息 | 用户 | 仅本人；房间会话属房间 |
| 记忆、画像 | 用户 | 仅本人 |
| 技能 | 用户或租户 | private / tenant |
| 定时任务 | 租户或用户 | 创建者 + 管理员 |
| 工作区、产物 | 用户 | 仅本人；按会话/房间校验 |
| 宠物包 | 租户 | tenant / private |

**租户切换的坑**：用户属于多个租户时，前端切换只改变 UI 选择；后台任务（定时任务、渠道回调、异步执行）必须在创建时固化租户，并在执行时重新校验成员资格，不能读取"当前租户"。

### 2.5 生命周期

- 注册：首个用户成为超级管理员；后续注册默认创建独立租户或走邀请（二选一，必须明确）。
- 邀请：邀请码/邮件，带过期与使用次数；加入后写成员关系。
- 停用：立即禁止登录与刷新；保留数据；可恢复。
- 离职/删除：转移或删除资源、吊销全部 refresh token、清理渠道绑定与外部身份。
- 租户停用：该租户所有用户不可登录，后台任务停止。
- 租户删除：软删 + 保留期 + 最终物理删除，需二次确认与审计。

### 2.6 服务身份

对外 API 不能用人类 JWT。至少需要：

- API Key：前缀 + 密文哈希存储、作用域（租户/智能体/权限）、过期、轮换、吊销。
- 调用审计：每次调用记录 key id、来源 IP、资源、结果。
- 限流：按 key 的 QPS/并发/日额度。
- 密钥展示：创建时明文仅显示一次，之后只显示掩码。

## 3. 本项目现状

### 3.1 已具备

| 能力 | 实现 |
|---|---|
| 租户/用户 | `Tenant`、`User`（`tenant_id` 为当前活动租户）、`TenantMembership` 多对多 |
| 角色 | `users.role`：`user / admin / superadmin`；`require_admin`、`require_superadmin` |
| 注册登录 | `/api/auth/register`、`/login`、`/refresh`、`/logout`；bcrypt；密码 ≥8 字符且 ≤72 字节 |
| 令牌 | access 默认 15 分钟、refresh 默认 7 天；refresh 仅存 SHA-256 哈希；刷新时轮转旧 token |
| 租户切换 | 用户可在所属租户间切换；`get_current_user` 校验成员资格 |
| 后台执行租户 | `core/execution_scope.py`：`require_execution_user`、`resolve_background_tenant`、`bind_execution_scope`，后台任务固化租户 |
| 资源可见性 | `agents`、`knowledge_bases`、`graph_knowledge_bases`、`pet_packages`、`hooks` 等有 `visibility: tenant/private` |
| 会话归属 | `core/session_access.py`：`authorize_session` / `owned_session`，会话必须是本人且非房间来源 |
| 管理入口 | `/api/admin/users`（superadmin）、`/api/tenants`（superadmin）、租户成员增删 |
| 前端 | 登录/注册、租户切换、用户管理、租户管理页 |

### 3.2 部分具备

- **隔离**：应用层 `tenant_id` + `user_id` 过滤；RLS 只覆盖 5 张用户级辅助表（`chat_runs`、`chat_run_events`、`memory_changes`、`memory_versions`、`memory_organize_plans`）。核心业务表没有数据库兜底。
- **角色**：只有全局角色，且 `TenantMembership` 无角色字段；"租户管理员"实际上等于全局 `admin`，无法表达"只管理某个租户"。
- **可见性**：只有 `tenant/private` 两档，没有"指定成员/部门"；`private` 的判断分散在各路由（如 `visibility == "tenant" OR created_by == user`），没有统一策略函数。
- **停用**：`is_active=false` 后登录与 refresh 被拒绝；已签发的 access token 在剩余有效期内仍可用，直到下一次请求查库（当前 `get_execution_user` 每次都查 `User.is_active`，实际窗口很小），但不会主动吊销。
- **邀请**：依赖管理员直接创建用户或加入成员，没有完整邀请流程。

### 3.3 缺失

- SSO（OIDC/SAML）、LDAP/AD、SCIM、MFA。
- 租户内角色与资源级 ACL。
- 部门/项目层级。
- 服务账号、API Key、OAuth Client Credentials。
- 登录失败锁定、异常登录检测、会话设备管理。
- 权限判定的统一策略层（当前散落在各路由）。
- 权限变更的审计（见 D10）。
- 离职/删除的自动化清理。

| JWT | `auth/jwt_handler.py` |

## 4. 目标设计

### 4.1 数据模型增量

**租户内角色**

```
tenant_memberships
  tenant_id, user_id, role, status, joined_at
  role: owner | admin | member | viewer
  status: active | invited | suspended
```

**资源 ACL**

```
resource_grants
  id, tenant_id, resource_type, resource_id
  principal_type: user | tenant_role | department
  principal_id
  actions: text[]  -- read/edit/delete/publish/invoke
  created_by, created_at
  UNIQUE(resource_type, resource_id, principal_type, principal_id)
```

**部门**

```
departments
  id, tenant_id, parent_id, name, path
user_departments
  user_id, department_id
```

**服务账号**

```
service_accounts
  id, tenant_id, name, description, status, created_by
api_keys
  id, service_account_id, key_prefix, key_hash, scopes, expires_at,
  last_used_at, revoked_at, created_at
```

### 4.2 统一授权入口

新增 `authz` 模块，所有路由只调用统一函数，禁止各自拼 where：

```
require_tenant(user, tenant_id)                      # 成员资格 + 租户状态
can(user, action, resource) -> bool                  # 角色 + 可见性 + ACL
scope_query(query, user, resource_type) -> query     # 在 SQL 层追加过滤
require(resource, action) -> None                    # 不满足则 403/404
```

**返回语义**：无权访问统一返回 404，避免泄露资源是否存在；仅管理员操作返回 403。

### 4.3 认证扩展

- OIDC：授权码 + PKCE；`id_token` 校验 issuer/audience/nonce；按 `email` 或 `sub` 绑定用户；首次登录走邀请或 JIT（可配置）。
- SAML：断言签名校验、属性映射、单点登出。
- SCIM：用户/组的增删改同步，删除即停用。
- MFA：TOTP，敏感操作（创建 API Key、修改权限、导出数据）强制二次验证。

### 4.4 服务身份

- API Key 只存哈希；展示一次。
- scope 至少包含：允许的智能体、允许的操作、租户。
- 每次调用记录 `api_key_id`，接入 D10 审计与 D12 计量。
- 支持按 key 限流与配额。

## 5. 失败模式

| 场景 | 后果 | 防护 |
|---|---|---|
| 后台任务读取 UI 当前租户 | 用户切换租户后任务写到错误租户 | 执行时使用固化租户 + 重新校验成员资格（已有 `execution_scope`） |
| 用户停用但 access token 未过期 | 短期内仍可调用 | 每次请求查 `is_active`；敏感操作二次校验；缩短 access TTL |
| `visibility=tenant` 被当作"部门可见" | 越权读取 | 引入显式 ACL；不要复用 visibility 表达复杂授权 |
| 先检索后过滤 | 泄露数量与存在性 | 查询层过滤；权限条件进 SQL |
| 跨租户管理员 | 一个 admin 管理所有租户 | 引入租户内角色；全局 admin 只做平台运维 |
| 删除租户未清理对象存储 | 数据残留 | 删除流程编排：DB → 对象存储 → 沙箱工作区 → 渠道 |
| 邀请链接被转发 | 非预期用户加入 | 一次性、绑定邮箱、过期、审计 |
| API Key 泄露 | 长期未授权访问 | 前缀可识别、哈希存储、轮换、吊销、异常调用告警 |

## 6. 实施路线

### P0（交付阻断）

1. **租户内角色**：`tenant_memberships.role`，替换全局 admin 的租户管理语义；提供成员管理 UI。
2. **统一授权层**：抽取 `authz`，先覆盖智能体、知识库、会话、记忆四类资源；所有列表查询走 `scope_query`。
3. **服务账号与 API Key**：支持创建/轮换/吊销、scope、最后使用时间；Agent API 接受 API Key。
4. **停用即时生效**：权限或状态变更时删除该用户全部 refresh token；敏感端点校验数据库状态与角色。
5. **SSO（至少 OIDC）**：登录页支持企业登录；首次登录绑定/邀请策略可配置。

### P1

6. 部门/项目层级与按部门授权。
7. 资源级 ACL 表与授权 UI。
8. MFA、登录失败锁定、异常登录提醒。
9. SCIM/LDAP 同步。
10. 会话设备管理与主动下线。

### P2

11. OAuth Client Credentials。
12. 细粒度数据权限（知识库文档级）。
13. 权限模拟/自查工具（"为什么我看不到这个资源"）。

## 7. 验收标准

- [ ] 普通用户无法通过任何 API 读取其他租户的资源（含列表、详情、导出、统计）。
- [ ] 用户属于多个租户时，后台任务始终写入创建时固化的租户。
- [ ] 租户管理员只能管理本租户成员与资源，不能访问平台级配置。
- [ ] 资源可设置为"仅本人 / 租户内公开 / 指定成员或部门"，判定逻辑统一。
- [ ] 知识库检索在 SQL 层按调用者权限过滤。
- [ ] 用户停用后 1 分钟内所有 refresh token 失效，敏感操作拒绝。
- [ ] 支持 OIDC 登录，且首次登录有明确的绑定/邀请策略。
- [ ] API Key 可创建、轮换、吊销，明文只展示一次，调用可追溯到 key。
- [ ] 权限变更、成员变更、API Key 变更全部产生审计记录（对接 D10）。

**回归测试建议**：
`backend/tests/test_tenant_isolation.py`、`test_session_access.py`、`test_users_admin.py`、`test_tenants.py`，并新增跨租户矩阵测试（用户 × 资源 × 操作）。

| 审计日志 | `audit_logs` | `user_id`（可空） | 用户级 | 建议补 `tenant_id` |

关联表跟随主资源：`agent_relationships`、`agent_skills`、`agent_knowledge_bases`、`agent_versions`、`skill_versions`。

**判定口径**：
- 需要租户内共享 → 租户级，加 `tenant_id`；还需区分仅创建者 → 加 `visibility` + `created_by`。
- 仅本人 → 用户级，加 `user_id`。
- 跨租户公开 → 扩展 visibility 值域，不省略归属字段。
- 全局唯一 → 全局级，不加归属字段，但必须限制为管理员可写。

## 附录 B 执行租户契约

用户切换界面租户只改变后续管理操作的筛选条件，不取消已运行任务，不改变已有对象的模型、工具、画像、记忆写入或观测归属。

| 执行入口 | 租户来源 | 权限依据 |
|---|---|---|
| 自动/手动定时任务 | `CronJob.tenant_id` | 活跃用户、活跃租户、成员资格、智能体可见性；手动触发校验所有者 |
| IM 消息及斜杠命令 | `ChannelConfig.tenant_id` | 渠道启用、渠道绑定、成员资格、资源权限 |
| 协作房间 | `ChatRoom.tenant_id` | 房间归属、成员资格、智能体权限；心跳检查实际成员资格 |
| Web / WebSocket / 发布版 API / 宠物会话 | 会话绑定的 `Agent.tenant_id` | 用户身份、会话归属、成员资格、智能体可见性 |
| 新的无智能体交互 | 入口处捕获一次当前租户 | 入口权限校验；后续沿用捕获值 |
| 已有子智能体 | 父执行租户 | 父子关系、成员资格、子智能体可见性、知识库权限 |
| 临时子智能体 | 父执行租户 | 父任务上下文、工具白名单、委派层级限制 |
| 记忆提取 / 每日记忆 | 来源会话的智能体及入口捕获租户 | 会话所有权、来源一致性、成员资格 |
| 知识图谱抽取 | 来源知识库的租户 | 沿用知识库归属，不按当前租户选模型 |

**实现规则**：
1. `require_execution_user` 校验用户/租户启用状态与 `tenant_memberships`；切换界面不影响仍有效的执行。
2. 按执行租户和 `visibility/created_by` 加载资源；不得移除租户条件，也不得写 `User.tenant_id` 模拟身份。
3. `bind_execution_scope` 绑定用户、租户、智能体上下文；`AgentLoop.run` 为并发工具任务传播，并在结束、异常、取消时清理。
4. 直接实例化 `AgentLoop` 也必须显式传入执行租户；观测与 Hook 读取该值，不用用户级缓存。
5. 跨请求的记忆任务携带来源信息并重新授权；来源缺失、成员移除、租户停用或租户不一致时，不调用模型、不写入。
6. 对象执行路由用 `ExecutionUser`（仅验 JWT 与用户状态），随后必须校验对象所有权与租户；新建/管理入口才用 `CurrentUser`。
7. 权限撤销后，房间 SSE 应发送 `access_revoked` 并结束连接。
