# D02 智能体运行时

> **解决什么问题**：一次用户请求如何被转换成可流式观察、可中断、可恢复的多轮推理与工具执行，并在上下文窗口内稳定完成。
> **适用读者**：后端运行时与接口开发、前端 SSE/任务恢复接入、测试与交付排障。
> **关联文档**：[D03 模型接入与治理](D03-模型接入与治理.md) · [D04 工具与外部集成](D04-工具与外部集成.md) · [D07 多智能体协作](D07-多智能体协作.md) · [D13 可靠性与性能](D13-可靠性与性能.md) · [能力全景 §5 D2](../企业级Agentic平台能力全景.md)
> **状态基准**：2026-11 代码。状态统一用 `已具备 / 部分 / 缺失`。

---

## 1. 边界

**负责**：
- 决策循环：ReAct、最大迭代、停止条件、并行与取消。
- 上下文工程：预算、截断、工具结果压缩、历史摘要、溢出兜底。
- 流式协议：事件模型、SSE 帧、序号与重放、客户端幂等依据。
- 后台执行：任务脱离请求生命周期、断线重连、停止、续跑。
- 状态与恢复：消息、快照、工具结果未知语义。
- 提示词组装、运行环境查询，以及运行时入口的执行/接口契约。

**不负责**：
- 模型目录、路由、配额与供应商密钥 → D03。
- 工具实现、MCP 连接与沙箱隔离 → D04。
- 多智能体编排策略与预算传播 → D07。
- 队列、容量、SLO 与多实例部署验证 → D13 / D14。

**设计底线**：每次执行必须有唯一 owner、单调事件序号和明确终态；没有代码支撑的压缩表、死循环检测、跨进程迁移，一律按“缺失”记录。

## 2. 能力清单

### 2.1 决策循环

| 能力 | 应该提供 | 关键设计点 / 坑 |
|---|---|---|
| ReAct 循环 | 推理 → 工具 → 结果注入 → 再推理 | 工具结果必须作为 `role=tool` 消息回填，且与 `tool_call_id` 一一对应 |
| 最大迭代与停止 | 硬上限、无工具调用终答、用户停止、超时、权限撤销 | 上限是兜底不是完成条件；取消要覆盖流式读取、工具执行、确认等待三段 |
| 死循环检测 | 连续重复工具调用/重复参数熔断 | 仅靠 `max_iterations` 会在烧掉大量 token 后才停 |

### 2.2 上下文工程

| 能力 | 应该提供 | 关键设计点 / 坑 |
|---|---|---|
| 窗口预算 | 总窗口减输出预留；达到比例自动压缩 | 预算应来自模型能力；阈值过低会频繁摘要，过高会撞硬限制 |
| 分层截断与工具压缩 | 保留热区；老消息与图片截断；工具结果近期全量、中期截断、远期摘要 | 图片 base64 必须剥离；迭代内压缩与跨轮摘要不能互相替代 |
| LLM 摘要 | 结构化保留决策、指令、待办、关键路径 | 摘要失败要有非 LLM 兜底；增量摘要要带入旧摘要 |
| 溢出兜底 | 模型报超长时激进裁剪后重试一次 | 只裁剪内存消息不落库，重试后仍可能再次超限 |
| 压缩持久化 | 标记已压缩消息，避免重复摘要 | 只存 `context_summary` 而不标记消息，下次加载仍读全量 |

### 2.3 流式协议

| 事件组 | 事件 | 用途 |
|---|---|---|
| 文本 | `text_delta`、`thinking`、`reasoning` | 实时输出与推理展示 |
| 工具 | `tool_call`、`tool_result`、`file_changes` | 工具卡片、文件变更 |
| 交互 | `confirmation_required`、`confirmation_resolved`、`ui_action_*` | 人工确认与前端 UI 动作 |
| 任务 | `run`、`run_status`、`done`、`error`、`access_revoked` | 任务标识、终态、权限撤销 |
| 委派 | `delegation_start/end/thinking/text_delta/tool_call/tool_result/heartbeat` | 子 Agent 进度 |

**协议规则**：
- Web SSE 的 `data` 是 JSON，以 `type` 区分事件；持久任务额外带 `run_id`、`sequence`、`replay`。
- 已发布 API SSE 保留 `event:` 名称与 `text_delta.text` 字段；OpenAPI 用 `x-event-schema` 描述解码后的数据。
- `done` 必须等任务终态提交后才发，避免前端抢跑下一轮；空闲连接发送 `: ping` 保活。
- 客户端按 `run_id + sequence` 去重，重连时以最后消费序号作为 `after`。
- 权限在订阅期间持续复查，失效时发送 `access_revoked` 并结束。

注意：事件模型与前端强耦合，当前没有 schema 版本号；任何字段改名都是破坏性变更。

### 2.4 并发、取消与确认

- 同一批工具中，委派并发启动，普通工具顺序执行；委派结果按原始调用顺序回填。
- `AskUserQuestion` 与 `ui_*` 前端工具在 AgentLoop 内拦截，不能进工具执行器，否则等待回包会死锁。
- 确认等待必须可分片（带心跳）并受超时约束；SSE 断开时取消并清理 pending 状态。
- 取消后仍允许写终态，但不能借此恢复已撤销的外部读取权限；确认归属由服务端固定为执行租户，恢复和提交时复查成员资格。

### 2.5 后台执行

| 能力 | 应该提供 | 本项目做法 |
|---|---|---|
| 任务与请求解耦 | 断开 SSE 不终止执行 | `ChatRun` 持久化任务，HTTP 响应只是事件订阅者 |
| 并发约束 | 同一会话最多一个运行任务 | 会话行锁 + `status='running'` 部分唯一索引 |
| 重连 | 按游标回放并继续实时订阅 | `chat_run_events` 按 `(run_id, sequence)` 读取 |
| 停止 | 显式取消父任务与子任务并保存进度 | `stop_requested` + 本地 worker 取消 + 跨进程轮询 |
| 续跑 | 只在安全条件下允许 | 所有工具调用必须已有成功结果；否则提示先核对 |

**续跑语义**：续跑是“关联原任务的新一轮”，不是 Python 调用栈恢复，也不重新提交原始问题。同名同参数的已完成工具调用直接复用旧结果；结果未知的调用禁止一键续跑，因为失败响应也可能已在外部产生副作用。

### 2.6 状态与恢复

- 会话消息是长期事实；`chat_runs.snapshot` 是任务级实时快照，事件表是权威事件日志。文本增量按时间或条数批量提交；工具边界在推进下一步前提交。
- 中断时未保存结果的工具调用标记为 `unknown`，并在历史里补一条符合模型协议的工具响应，避免缺少 `tool_call_id` 结果导致后续请求失败。
- 强制终止可能丢失最后一个尚未提交的文本批次；已完成事件已持久化时，进程崩溃会恢复为已完成。

### 2.7 提示词与运行环境

- 系统提示由 Jinja2 模板组装，注入人格、记忆、技能、画像、工具清单与当前时间；发布快照明确的空提示词保持为空。
- `get_runtime_info` 是后端直接执行的只读工具，返回设备、系统、后端进程、时区、执行上下文，可选资源与沙箱状态；不绕过工具白名单，也不构成新的执行入口。设备标识是 hostname 哈希，容器内只能看到容器视角；Docker 可连接不等于代码可执行，因此返回 `execution_verified=false`。

### 2.8 执行与接口契约

| 契约 | 要求 |
|---|---|
| 执行用户 | 已有对象的执行/查询使用 `ExecutionUser`，先校验对象归属，不读取界面当前租户 |
| 会话绑定 | 请求 `agent_id` 必须与会话一致；显式改绑需同租户且无运行中任务 |
| 不可变归属 | `ChatRun.request` 的 `_execution_tenant_id`、`_execution_agent_id` 由服务端写入 |
| 模型冻结 | `PreparedExecution` 在一次执行内固定模型，历史格式与供应商调用使用同一模型 |
| 删除会话 | 仅 sessions 路由注册，成功返回 `204` 且无响应体 |
| SSE | `text/event-stream`；OpenAPI body 声明为字符串，`x-event-schema` 描述解码数据 |

## 3. 本项目现状

### 3.1 已具备

| 能力 | 实现 |
|---|---|
| ReAct 循环 | `core/agent.py` `AgentLoop`，最多 100 轮（`AGENT_MAX_ITERATIONS`） |
| 并行委派 | 普通工具串行，`delegate_task` 并发执行，结果按调用顺序回填 |
| 流式事件 | 类型化事件 + 兼容编码；事件集合见 `interface/contracts.py` |
| 流式断连重试 | 仅在本次迭代零产出时重试，最多 2 次，1s/2s 退避 |
| 上下文预算 | `ContextBudget`：窗口 128k、输出预留 8k、阈值 0.75；第 4 轮起压缩早期工具结果 |
| 跨轮摘要 | `prepare_context` 截断后按预算分割，LLM 摘要 + 非 LLM 兜底；`update_context_summary` 增量折叠并节流 |
| 溢出兜底 | `is_context_overflow_error` + `emergency_compress(level=1)`；同步 REST 与发布 API 会重试一次 |
| 后台任务 | `chat_runs` + `chat_run_events`，心跳 1s、租约 30s、同会话唯一运行任务 |
| 重连与停止 | `GET /runs/{id}/events?after=` 回放；`POST /runs/{id}/stop` 等待终态 |
| 安全续跑 | 复用已完成工具结果；结果未知的任务禁止续跑 |
| 执行契约与运行环境 | `core/execution.py`、`core/session_access.py`、`tools/runtime_info.py`；`test_api_contracts.py`、`test_execution_security.py` |

### 3.2 部分具备

| 能力 | 现状 | 缺口 |
|---|---|---|
| 取消与清理 | 停止会取消父任务和子任务 | 无轮次级墙钟超时；Docker 线程操作不可中断，只能等其结束 |
| 压缩持久化 | 摘要写入 `sessions.context_summary` | 没有 `messages.compressed_at` / `session_compressions`，每次加载仍读全量并重复摘要 |
| 溢出重试 | 同步 REST/发布 API 重试 | Web 后台流只发 warning 后报错，不重试；三条路径行为不一致 |
| 事件协议 | `sequence`/`replay` 已用于去重 | 无 schema 版本；运行指标口径分散 |
| 多实例 | 任务状态、重连、停止可跨副本 | 确认与浏览器动作管理器仍在进程内，需要会话粘性 |

### 3.3 缺失

- 死循环主动检测（连续重复工具调用/参数）。
- 轮次级墙钟超时与统一取消预算。
- 用户主动压缩（`/compact`）与压缩审计 API/UI。
- 运行时指标的统一聚合口径（每轮 token、工具耗时、首字延迟）；提示词模板的运行时版本化归 D09。

## 4. 关键设计

### 4.1 数据模型

```
sessions
  id, user_id, agent_id, context_summary, ...
      ├─ messages: 会话长期历史（user/assistant/tool）
      └─ chat_runs: 一次 Web 轮次
           id, session_id, user_id, assistant_message_id, status,
           owner, stop_requested, request, snapshot, last_sequence,
           heartbeat_at, resumed_from
              └─ chat_run_events: (run_id, sequence) 主键，payload JSONB
```

- `status`：`running / completed / failed / stopped / interrupted`。
- 续跑条件：状态属于 `stopped/failed/interrupted`，且快照中不存在结果未知的工具调用。
- `snapshot` 只保存任务级摘要，事件表才是重放事实源。

### 4.2 执行流程

1. `POST /api/chat/stream` 校验附件、会话与智能体一致性，`chat_runs.reserve` 加会话行锁并创建任务。
2. `ChatExecutionService.prepare` 冻结模型与供应商类型，加载历史并组装系统提示。
3. `prepare_context` 估算 token；超阈值先截断再摘要；溢出时由入口决定是否 `emergency_compress` 重试。
4. `AgentLoop.run` 以 demand-driven 方式产出事件；生产者消费并批量持久化，HTTP 响应作为独立订阅者回放并实时接收。
5. 工具调用事件在进入执行前持久化，工具结果在推进下一步前提交；文本增量按 0.1s 或 64 条批量提交。
6. 终态由生产者提交后再发 `done`；正常停机取消 worker 并写 `interrupted`，停止请求写 `stopped`。

### 4.3 失败模式与防护

| 场景 | 后果 | 现有防护 |
|---|---|---|
| SSE 断开 | 前端看不到进度 | 任务继续执行；按 `run_id + sequence` 重连回放 |
| 进程崩溃 | 任务卡在 running | 心跳超过 30s 后，状态查询或订阅时标记中断 |
| 数据库抖动 | 心跳写入失败 | 无法证明所有权时取消本地执行（fail closed） |
| 用户停止 | 子任务继续跑 | 取消父任务并取消已登记子任务；等待终态后才允许下一条 |
| 上下文溢出 | 模型拒绝请求 | 同步路径紧急压缩重试一次；后台路径仅告警 |
| 工具结果未知 | 续跑可能重复副作用 | 标记 `unknown`，禁止一键续跑，要求人工核对 |
| 重复启动 | 同一会话两个任务 | 行锁 + 部分唯一索引，返回 409 |
| 权限撤销 | 继续读取数据 | 订阅期间复查，发送 `access_revoked` 并结束 |

## 5. 实施建议

### P0

1. **死循环检测**：对“同名同参数工具调用连续出现 N 次”熔断，返回可解释错误并终止本轮。
2. **轮次级墙钟超时**：为整轮执行设置上限，覆盖模型流、工具执行、确认等待；超时走统一取消与终态写入。
3. **压缩持久化**：落地 `messages.compressed_at` 与 `session_compressions`，加载时只取活跃消息，避免重复摘要。
4. **统一溢出重试**：Web 后台路径与同步路径使用同一套紧急压缩策略，避免行为分叉。

### P1

5. 事件 schema 版本化，明确新增字段与破坏性变更规则。
6. 运行时指标统一：每轮 token、工具耗时、首字延迟、迭代次数进入同一聚合口径。
7. 确认与浏览器动作管理器外置，支持多副本无粘性部署。

### P2

9. 用户主动压缩（`/compact`）、压缩历史查询与“查看摘要”前端展示。

## 6. 验收标准

- [ ] 模型连续多次返回相同工具调用时，平台在有限轮次内熔断并给出可解释结果。
- [ ] 单轮执行有墙钟上限，超时后任务进入明确终态，子任务与工具调用被取消。
- [ ] 压缩后再次加载会话只读取活跃消息，不重复摘要；摘要包含决策、指令、待办与关键路径。
- [ ] 同步 REST、Web 后台流、发布 API 三条路径的溢出处理行为一致。
- [ ] 用户关闭浏览器后任务继续执行；重新进入会话能从最后序号恢复且不重复追加。
- [ ] 同一会话无法同时启动两个运行任务；运行中会话必须先停止才能删除。
- [ ] 停止、失败、中断后的任务仅在全部工具调用有成功结果时允许续跑。
- [ ] 权限撤销后 SSE 发送 `access_revoked` 并结束，不继续输出数据。
- [ ] 运行环境查询不绕过工具白名单，不返回环境变量、密钥或完整路径。
