# D11 可观测性与运营

> **解决什么问题**：Agent 的行为是概率性的，"看起来正常"不等于正常。没有日志、指标和调用链，就无法回答"Token 花在哪、哪里慢、哪里出错、昨天为什么变差"。
> **适用读者**：后端研发、SRE/运维、平台管理员、质量与运营。
> **关联文档**：[D12 成本与配额](D12-成本与配额.md) · [D14 部署交付与运维](D14-部署交付与运维.md) · [能力全景 §5 D11](../企业级Agentic平台能力全景.md)
> **状态基准**：2026-11 代码。状态只用 `已具备 / 部分 / 缺失`；设计目标不写成已实现。

---

## 1. 边界

**本文负责**：结构化日志、指标、调用链追踪；LLM/工具/Agent/会话/租户各层指标口径；告警规则与通知；会话级复盘；SLO 与错误预算。

**本文不负责**：成本计价、配额执行与账单（D12）；安全审计与合规留存（D10）；熔断、限流、队列等可靠性机制本身（D13）；回答质量评测与智能体评级（D09）。

**核心原则**：

1. **观测不能拖慢主链路**：采集异步化、失败只记日志、队列满丢数据保业务。
2. **明细是事实源，预聚合只是加速**：任何报表口径都要能回到明细复算。
3. **维度统一**：`tenant_id / user_id / session_id / agent_id / model / trace_id / 时间`，保证任意下钻。
4. **告警要可执行**：每条告警必须对应明确的排查入口和负责人，否则只是噪音。

## 2. 能力清单

### 2.1 日志

- 结构化日志（JSON 或键值对），带 `trace_id`、`session_id`、`tenant_id`。
- 分级与采样：错误全量、调试可开关、高频事件采样。
- 采集与保留：stdout → 日志采集器（Loki/ELK）→ 按天/容量轮转。
- 关键事件：LLM 失败、工具失败、队列溢出、迁移、启动阶段耗时。

### 2.2 指标

- **业务**：活跃用户、会话数、消息数、任务完成率、渠道调用量。
- **质量**：LLM 失败率、工具错误率、重试率、空回答率、压缩触发率。
- **性能**：TTFT P50/P95、端到端延迟 P95、工具耗时 P95、上下文利用率 P95。
- **容量**：沙箱并发占用、队列长度、写入滞后。

### 2.3 追踪

- 一次 Agent 执行一个 `trace_id`，内部按 `call_order` 串联 LLM 调用与工具调用。
- 追踪要能回答：每一轮用了哪个模型、多少 token、耗时、首 token 延迟；每次工具做了什么、输出多大、是否截断；是否触发压缩、压缩前后 token。
- 与日志、指标通过 `trace_id` 互相关联。

### 2.4 关键指标口径

| 指标 | 口径 |
|---|---|
| LLM 失败率 | 窗口内 `final_status=failed` 调用数 / 总调用数 |
| 工具错误率 | 窗口内 `is_error=true` 工具调用数 / 总工具调用数 |
| 延迟 P95 | 窗口内调用耗时 `duration_ms` 的 95 分位 |
| 缓存命中率 | `cache_read_tokens / prompt_tokens` |
| 上下文利用率 | `prompt_tokens / 模型 context_window` |
| 压缩触发率 | 触发压缩的 trace 数 / trace 总数 |
| 对话平均 token | trace `total_tokens` 总和 / trace 数 |
| 首响延迟 | 用户消息到首个 token 回流的时间 |

### 2.5 告警

| 告警 | 建议条件 | 级别 |
|---|---|---|
| LLM 失败率突增 | 10 分钟失败率 > 5% 且较前一周期翻倍 | P1 |
| 工具错误率超标 | 单工具 10 分钟错误率 > 20% | P2 |
| 延迟劣化 | LLM 延迟 P95 > 30s 持续 5 分钟 | P2 |
| 上下文接近满 | 利用率 P95 > 90% | P3 |
| 压缩频繁 | 压缩触发率 > 30% | P3 |
| 采集异常 | 队列溢出、写入失败持续出现 | P2 |
| 沙箱/渠道断线 | 沙箱启动失败率、渠道回调失败率超阈值 | P2 |

### 2.6 复盘

- 按会话或 trace 一键还原完整执行轨迹（LLM → 工具 → 下一轮）。
- 支持标注 badcase、记录根因、关联到提示词/工具/模型变更。
- 复盘结论可回流为测试用例或优化项。

### 2.7 SLO

- 可用性：API 成功率、SSE 建连成功率。
- 延迟：TTFT P95、端到端 P95。
- 质量：对话成功率（completed / 全部 trace）、工具成功率。
- 每个 SLO 配错误预算与燃尽告警，超预算时冻结非必要变更。

## 3. 本项目现状

### 3.1 已具备

| 能力 | 实现 |
|---|---|
| 调用明细 | `llm_call_logs`：模型、供应商、token、缓存 token、TTFT、耗时、吞吐、重试、状态、错误类型、stop_reason、温度、工具数 |
| 工具明细 | `tool_call_logs`：工具名、执行类型、耗时、错误、参数/输出体量、估算注入 token、截断、并发标记 |
| 执行明细 | `agent_trace_logs`：状态、轮数、工具数、token、耗时、压缩字段、是否顶到最大迭代 |
| 异步采集 | `observation/recorder.py`：有界队列 20000，每 2s 或 500 条批量写入，失败只记日志 |
| 预聚合 | `token_usage_daily`（用户×日×模型）、`tool_usage_daily`（用户×日×工具）、`performance_daily`（租户×日） |
| Langfuse | `observation/client.py`；Chat SSE 每轮创建 `chat` 根 span，LLM/工具作为子 observation |
| 管理观测接口 | `/api/observability/overview`、`/traces`、`/traces/{id}`、`/stats`、`/tool-ranking`、`/tools/{tool}/trend`、`/quality`，强制 admin |
| 用量报表接口 | `/api/analytics/summary`、`/trend`、`/distribution`、`/detail`，支持 mine/global |
| 前端 | `/observability` 五个 Tab：实时监控、Trace 明细、聚合报表、工具排行、对话质量；`/usage` 个人/全局用量 |
| 采集隔离 | 所有采集 fire-and-forget；队列满丢弃新记录并每 300s 打一次 `observation_queue_overflow` |

### 3.2 部分

- **追踪只覆盖 Web 对话**：Langfuse 根 span 在 `interface/routes/chat.py` 创建；cron、渠道、宠物、聊天室没有根 span，跨入口追踪不完整。
- **错误链路缺 trace**：`AgentLoop` 仅在正常完成或顶到最大迭代时写 `agent_trace_logs`；LLM 抛异常、用户取消没有 finally 兜底，`finalize_trace_error()` 目前无调用方，trace 错误率会偏低。
- **压缩字段未落库**：`agent_trace_logs` 有 `is_compressed / saved_tokens` 等列，但 `_finalize_trace()` 未传这些字段，因此 `performance_daily.compress_count` 与质量页压缩指标恒为 0；压缩信息只出现在 SSE 事件和 Hook 数据里。
- **上下文利用率未采集**：`llm_call_logs.context_window / context_utilization` 两列没有写入点，Overview 的上下文利用率 P95 恒为空。
- **状态枚举不完整**：trace 实际只写 `completed / timeout / error`，没有 `interrupted`；用户中止与异常都归到 error 或丢失。
- **指标无实时出口**：没有 `/metrics`，没有 Prometheus/Alertmanager；"实时监控板"实际是查明细表的分桶聚合，按窗口轮询刷新。
- **权限只到全局管理员**：`/api/observability` 与 `/api/analytics?scope=global` 只校验 `admin/superadmin`，查询未按租户过滤，跨租户可见。
- **日志是控制台文本**：使用 structlog 默认输出，未配置 JSON、trace 注入、采集器或轮转；`LOG_LEVEL` 仅传给 uvicorn。
- **明细永久保留但无分区**：设计建议月分区，当前三张明细表为普通表，只有常规索引。

### 3.3 缺失

- 告警规则引擎、通知通道（企微/飞书 webhook）、告警历史与静默。
- SLO 定义、错误预算、燃尽率。
- 会话级"一键复盘"入口与 badcase 标注回流。
- 质量指标：回答采纳率、人工介入率、重复提问率、无效/重复工具调用率。
- CSV 导出（设计有，接口与前端均未实现）。
- 异常检测、指标采样、明细表分区与归档策略。
- 成本维度指标（`cost_usd` 恒为 0，见 D12）。

## 4. 关键设计

### 4.1 埋点模型

```
一次 AgentLoop.run()
  trace_id (UUID), ObsContext 存入 contextvars
    ├── LLM 调用 —— call_order 由 ObsContext 自增
    ├── 工具调用 —— trace_id/session/user/tenant/agent 自动补齐
    └── 结束 —— 汇总 iteration/tool/token/duration 写 agent_trace_logs

recorder: asyncio.Queue(20000) → 每 2s 或 500 条 → 单事务批量 INSERT
          └── 同事务 UPSERT tool_usage_daily / performance_daily
```

- `ObsContext` 通过 `contextvars` 传递，LLM 客户端和工具执行器无需显式传维度。
- 工具记录由 `ToolExecutor` 和 `AgentLoop`（委派等并发工具）双点写入；`call_order` 在工具路径上默认 1，排序主要依赖 `created_at`。
- 写失败不重试；队列满丢的是**新到记录**，且日志限流 300s。
- `token_usage_daily` 走独立链路 `core/usage.py`，与明细采集不共享事务。

### 4.2 三层数据与查询路径

| 层 | 表 | 用途 | 现状 |
|---|---|---|---|
| 明细 | `llm_call_logs` / `tool_call_logs` / `agent_trace_logs` | 精确聚合、Trace 下钻 | 已具备，无分区 |
| 预聚合 | `token_usage_daily` / `tool_usage_daily` / `performance_daily` | 报表、排行 | 已具备，采集时同步 upsert |
| 实时指标 | Prometheus `/metrics` | 实时告警与 P95 | 缺失 |

查询策略：1 小时/24 小时按分钟/小时桶查明细表；7 天以上查预聚合或按日桶聚合；Trace 下钻按 `trace_id` 查明细。P95 使用 PostgreSQL `percentile_cont`。

### 4.3 指标口径注意事项

- `performance_daily` 存的是累计值，平均值需查询时用总量/次数计算，不存均值，避免预聚合失真。
- `tool_usage_daily` 的维度是 **user**，不是 tenant；按租户出工具报表需要回查明细。
- `context_utilization` 与压缩收益是"有列无数据"，展示前应先补写入点，否则会出现"功能在但永远为 0"的误导。
- `token_usage_daily.cost_usd` 固定写 0，任何费用口径不可用。
- 所有时间桶按 UTC 截断；`token_usage_daily.date` 按服务器本地日期，两者跨时区可能相差一天。

### 4.4 告警与 SLO 落地方式

```
LLM/工具/队列埋点 → Prometheus Counter/Histogram → Alertmanager → 飞书/企微 webhook
                                            └→ Grafana / 现有观测页
```

- 告警规则应版本化在仓库内，阈值可按租户覆盖。
- SLO 建议先落两条：对话成功率 ≥ 99%，TTFT P95 ≤ 5s；错误预算按周滚动。
- 告警去重与静默必须做，否则失败率抖动会淹没值班。

## 5. 实施建议

### P0（先让数据可信、告警可用）

1. 补齐 trace 错误/取消路径：在 `AgentLoop.run()` 用 `finally` 兜底写 trace，区分 `interrupted / error / timeout`。
2. 写入压缩字段与 `context_window / context_utilization`，让质量页与上下文告警有真实数据。
3. 增加 `/metrics`（prometheus-client）与最小告警集：LLM 失败率、工具错误率、延迟 P95、采集队列溢出、写入失败。
4. 修复观测与报表接口的租户过滤，避免租户管理员上线后跨租户泄露。
5. 采集写入失败与队列溢出纳入告警，并暴露队列长度、写入滞后指标。

### P1（运营闭环）

6. 告警规则可配置 + 告警历史 + 静默；接入飞书/企微。
7. 会话/trace 一键复盘：从观测页跳转会话，展示完整输入输出与工具结果。
8. badcase 标注与回流，关联提示词/工具版本。
9. SLO 看板与错误预算燃尽告警。
10. CSV 导出（复用当前筛选条件）。

### P2（规模化与智能化）

11. 明细表按月分区、冷热分层与保留策略。
12. 高频事件采样与指标基数治理。
13. 质量指标：采纳率、人工介入率、重复提问率、无效工具调用率。
14. 异常检测（同比/环比突增、工具耗时漂移）与根因提示。
15. 结构化日志接入采集平台，统一 `trace_id` 检索。

## 6. 验收标准

- [ ] 任意一次对话都能通过 `trace_id` 还原 LLM 调用、工具调用、压缩事件的完整顺序。
- [ ] LLM 失败、工具失败、超时、用户取消都能在 trace 明细中看到，且状态区分正确。
- [ ] 监控板上的失败率、P95、TTFT、token 速率与明细表复算结果一致。
- [ ] 上下文利用率与压缩收益不再是恒 0/恒空。
- [ ] 失败率突增、工具错误率超标、延迟劣化能在 5 分钟内触发告警并送达指定通道。
- [ ] 告警可查看历史、可静默、阈值可配置。
- [ ] 管理员可按租户筛选观测数据；租户管理员只能看到本租户。
- [ ] 能按模型、智能体、用户、租户查看 token/耗时/错误分布，并导出与筛选一致的 CSV。
- [ ] 采集故障（队列溢出、写入失败）自身有告警，且不影响对话主链路。
- [ ] 有明确的 SLO 与错误预算，超预算时有处理流程。
- [ ] 日志可按 `trace_id` 检索，保留期满足运维要求。
