# D09 智能体生命周期与质量

> **解决什么问题**：企业不是“建一个智能体就完事”，而是持续运营几十上百个智能体。需要回答：谁改了提示词、当前线上是哪个版本、改坏了多久能回滚、上线前有没有回归、线上效果如何。
> **适用读者**：产品/运营、后端、平台管理员、交付实施、质量负责人。
> **关联文档**：[D02 智能体运行时](D02-智能体运行时.md) · [D03 模型接入与治理](D03-模型接入与治理.md) · [D11 可观测性与运营](D11-可观测性与运营.md) · [D15 开放平台与生态](D15-开放平台与生态.md) · [能力全景 §5 D9](../企业级Agentic平台能力全景.md)
> **状态基准**：2026-11 代码。状态只用 `已具备 / 部分 / 缺失`；旧文档中的权限矩阵与当前代码不一致处，以代码为准。

---

## 1. 边界

**本文负责**：智能体定义、配置管理、版本快照、发布与回滚、模板与复用、评测、线上质量反馈、A/B、归档下线；以及作为可复用资产的技能生命周期。

**本文不负责**：运行时循环与上下文（D02）、模型选择策略（D03）、工具契约（D04）、知识库检索（D05）、可观测数据底座（D11）、对外协议与生态（D15）。

**核心原则**：

1. **草稿与线上分离**。编辑中的配置不得直接影响已发布的对外 API。
2. **版本必须可复现**。同一版本号应冻结提示词、模型、工具、技能、子智能体等全部运行时输入。
3. **发布必须有门禁**。至少经过配置校验；企业场景还需要审批、灰度与回滚。
4. **质量要闭环**。线上反馈与 Trace 要能回流成评测用例，而不是停留在点赞/点踩。
5. **下线要有依赖检查**。删除前确认无子智能体、渠道、定时任务、外部调用方依赖。

## 2. 能力清单

| 能力 | 企业级要求 | 对应设计点 |
|---|---|---|
| 定义 | 角色、提示词、模型、工具、知识库、记忆策略、预算 | 配置完整、可校验 |
| 版本与发布 | 草稿/发布分离、快照、差异、回滚、审批、灰度 | 版本不可变、可追溯 |
| 模板与复用 | 智能体模板、复制、导入导出、市场 | 降低重复建设 |
| 评测与质量 | 离线评测集、回归、评分维度、badcase 回流、A/B 对比 | 上线门禁与质量闭环 |
| 归档下线 | 依赖检查、数据保留、调用方通知 | 安全退场 |
| 技能资产 | 版本、验证、使用/成功率、市场同步、废弃 | 可复用且可治理 |

| 运行时质量数据 | `agent_trace_logs` + `/api/observability/quality` 提供成功/失败/中断、平均耗时、平均 token、每轮调用数、压缩率 |

### 3.2 部分

| 事项 | 代码事实 | 影响 |
|---|---|---|
| 版本快照完整性 | 快照记录 `skill_ids / child_ids`，但执行时技能与子智能体仍从**实时** `agent.skills / agent.children` 加载；`enabled_tools` 为空会启用全部非前端工具 | 旧版本不可完全复现；无法发布“明确不启用工具”的版本 |
| 权限模型 | 编辑/删除仅创建者，管理员不能代为操作；发布路由依赖 `AdminUser`，实际只有 admin/superadmin 能发布，owner 分支对非管理员不可达 | 与旧文档的“管理员可治理所有/所有者可发布”不一致 |
| 版本管理 | 只有发布与列表，没有差异对比、回滚、审批、灰度；版本号默认 UUID 前 8 位 | 改坏后只能重新发布，无法一键回到旧版 |
| 线上反馈 | 仅外部 API 会话支持 `up/down`，写入 `Message.token_usage["feedback"]`；Web 聊天无入口，无聚合 | 反馈无法用于质量分析 |
| 智能体概览统计 | `/api/agents/{id}/stats` 只返回会话数、消息数、最后活跃时间 | 旧文档的“调用次数、平均耗时”未实现 |
| 模板与复用 | 提示词模板是前端静态常量；无智能体模板、复制、导入导出、市场 | 新建智能体仍需手工配置 |
| 技能治理 | `is_public` 字段存在，但列表/搜索只过滤 `user_id`，公共技能不会出现在他人结果中；PRD F3.3 的自动提取未实现 | 平台公共技能不可发现；自学习闭环缺失 |
| 归档下线 | 只有 `is_active` 与硬删除；无依赖检查、数据保留策略、调用方通知 | 删除可能破坏子智能体/渠道/定时任务 |

## 4. 关键设计

### 4.1 定义模型

**现状**：`Agent` 同时承担“草稿配置”和“运行时配置”两个角色；发布时复制一份 JSON 快照到 `AgentVersion`。

**目标**：明确三类对象

```
Agent              稳定身份：名称、图标、归属、可见性
AgentDraft         可编辑配置：提示词、模型、工具、技能、知识库、子智能体
AgentVersion       不可变快照：配置 + 依赖版本 + 发布信息
```

`AgentVersion` 建议补充：

```
status / parent_version_id / traffic_percent   -- 状态、回滚来源、灰度比例
resolved_refs   JSONB  -- 技能/知识库/子智能体的具体版本与内容摘要
approval        JSONB  -- 审批人、时间、意见
```

### 4.2 发布流程

**现状**：

```
admin 点击发布 → 停用旧 is_active → 写入新快照 → is_active=true → 对外 API 立即使用
```

无审批、无灰度、无回滚、无差异对比，发布是“全量瞬时切换”。**目标状态机**：

```
draft → 校验 → 待审批 → 已发布(灰度 x%) → active → archived
                  ↑                         │
                  └──────── 回滚 ───────────┘
```

关键规则：

1. 发布前校验：模型存在且启用、工具存在、技能/知识库同租户、子智能体无环。
2. 快照冻结全部运行时输入，包括技能内容版本与子智能体版本，不能只存 ID。
3. 全量切换前支持灰度：按租户/用户/百分比分流，指标达标再扩大。
4. 回滚只需把旧版本置为 active，禁止修改历史快照。
5. 所有发布/回滚写审计日志（谁、何时、从哪个版本到哪个版本、原因）。

### 4.3 评测体系

**当前为缺失，以下为目标设计。**

```
eval_sets(id, tenant_id, agent_id, name) / eval_cases(id, set_id, input, expected, assertions)
eval_runs(id, set_id, agent_version_id, model_id, status) / eval_results(id, run_id, case_id, score, passed, judge)
```

评分维度：正确性、工具使用、指令遵循、成本、延迟、安全性。门禁建议：

| 指标 | 门禁 |
|---|---|
| 通过率 | 不得低于上一版本 - 2pp |
| 平均 token | 不得高于上一版本 + 15% |
| P95 延迟 | 不得高于上一版本 + 20% |
| 工具错误率 | 不得高于 5% |
| 安全用例 | 必须 100% 通过 |

实现顺序：先固定用例 + 规则断言（关键词/工具调用/JSON 结构），再引入 LLM-as-judge 与人工抽检。

### 4.4 线上质量闭环

```
用户反馈 / Trace 异常 / 人工抽检 → 标记 badcase → 补充 eval_set
  → 修复提示词/工具/模型 → 回归评测 → 灰度发布
```

现状只有 Trace 汇总和外部 API 反馈，缺少 badcase 表、归因字段、回流入口。建议新增 `quality_feedback` 表，统一存 `message_id / agent_version_id / rating / reason / tags / reviewer`，不要复用 `token_usage` JSONB。

### 4.5 技能资产生命周期

```
创建/导入(skills.sh) → 测试 → 使用 → report_skill_result(证据校验)
  → 版本迭代(SkillVersion 归档) → 验证失败停用 → 废弃
```

现状已覆盖版本、包、市场同步、结果上报与证据校验。缺口：自动提取、平台公共技能发现、技能质量看板、冷门技能降级策略。

### 4.6 权限矩阵（代码事实）

| 操作 | 旧文档 | 当前代码 |
|---|---|---|
| 创建 | 所有用户 | 所有登录用户（`CurrentUser`） |
| 编辑 | 创建者；管理员可编辑所有 | **仅创建者**；管理员不能代为编辑 |
| 删除 | 创建者；管理员可删除所有 | **仅创建者**；管理员不能代为删除 |
| 发布版本 | 管理员或所有者 | **仅 admin/superadmin**（`AdminUser`）；owner 分支不可达 |
| 查看/对外调用 | 同租户可见或本人 private；已登录用户可调用 | 一致；对外调用额外要求会话所有者 + 已发布版本 |

这张表必须与 D01 的 RBAC 设计对齐；当前实现是“创建者自治 + 管理员只管模型/观测”，不是企业常见的“管理员可治理所有资源”。

### 4.7 失败模式

| 场景 | 当前行为 | 风险 | 目标 |
|---|---|---|---|
| 发布错误提示词 | 立即全量生效 | 线上效果骤降 | 评测门禁 + 灰度 + 回滚 |
| 修改技能后调用旧版本 | 实时加载新技能 | 版本不可复现 | 快照冻结技能版本 |
| 删除被依赖的智能体 | 硬删除并清理关系 | 子智能体/渠道/任务断裂 | 依赖检查 + 软归档 |
| 空工具配置 | 对外执行启用全部工具 | 权限放大 | 区分“未配置”与“明确为空” |
| 反馈丢失 | 存在 JSONB，无查询 | 无法闭环 | 独立表 + 聚合 |

## 5. 实施建议

### P0（先让版本可信）

1. **冻结快照依赖**：技能内容版本、子智能体版本、知识库版本写入快照；执行只读快照。
2. **区分空工具语义**：`enabled_tools=[]` 表示明确不启用工具；未配置用 `null`。
3. **权限对齐**：明确管理员是否可治理他人智能体；当前代码与文档二选一并统一。
4. **版本不可变与回滚**：租户内版本号唯一；禁止修改历史快照；提供回滚接口并写审计。

### P1（质量门禁）

5. 评测集与回归运行：先规则断言，后 LLM-as-judge。
6. 发布前自动跑评测，未达标阻断。
7. badcase 表与回流入口；Web 聊天也支持反馈。
8. 按智能体质量看板：成功率、平均耗时/token、反馈分布、版本对比与配置 diff。

### P2（规模化运营）

9. 灰度发布与 A/B 分流。
10. 智能体模板/复制/导入导出/市场。
11. 下线依赖检查、数据保留与调用方通知。
12. 技能自动提取与公共技能治理、冷门降级；发布审批流与变更单集成。

## 6. 验收标准

- [ ] 修改技能或子智能体后，旧发布版本的对外行为保持不变。
- [ ] 能对比任意两个版本的配置差异，并一键回滚到旧版本。
- [ ] 发布前自动跑评测，未达门禁时无法发布。
- [ ] 对外 API 只使用已发布快照，不受编辑中配置影响。
- [ ] `enabled_tools=[]` 的版本不会暴露任何工具。
- [ ] 管理员/创建者的编辑、删除、发布权限与文档一致，并有测试覆盖。
- [ ] 用户反馈可在后台按智能体、版本聚合查询，并能转为评测用例。
- [ ] 公共技能能被其他用户搜索到并使用（若产品要求）。
- [ ] 删除智能体前会提示依赖（子智能体、渠道、定时任务、外部调用）。
- [ ] 每次发布、回滚、归档都有审计记录（操作人、时间、版本、原因）。
