# D14 部署交付与运维

> **解决什么问题**：企业客户大量要求私有化与内网部署，"能跑起来"只是起点；还需要可重复安装、可升级、可回滚、可备份恢复、可排查故障。交付能力本身就是产品能力。
> **适用读者**：交付实施、SRE/运维、后端研发、售前与客户成功。
> **关联文档**：[D11 可观测性与运营](D11-可观测性与运营.md) · [D12 成本与配额](D12-成本与配额.md) · [能力全景 §5 D14](../企业级Agentic平台能力全景.md) · [用户与租户隔离](D01-身份组织与权限.md)
> **状态基准**：2026-11 代码与 Compose 配置。状态只用 `已具备 / 部分 / 缺失`。

---

## 1. 边界

**本文负责**：部署形态、交付物、依赖清单、配置与密钥、升级与回滚、备份恢复、日常运维与容量基线。

**本文不负责**：应用层可靠性机制（队列、熔断、多实例一致性，见 D13）；监控告警规则与 SLO（D11）；租户配额与计费（D12）；具体渠道/浏览器网关的功能配置（各自文档）。

**核心原则**：

1. **可重复安装**：同一份 Compose 与配置在开发、测试、客户环境得到同样结果。
2. **升级前必须可回滚**：数据库迁移、对象存储、配置三部分都要有退路。
3. **密钥不进镜像、不进仓库**：由环境变量或密钥管理系统注入；备份必须演练，未演练的备份不算备份。

## 2. 能力清单

### 2.1 部署形态

| 形态 | 说明 |
|---|---|
| SaaS 多租户 | 单套平台服务多个租户，应用层按 `tenant_id` 隔离 |
| 私有化单机 | 客户机房单机 Docker Compose，基础服务与应用分离 |
| 内网/离线 | 无外网环境，镜像与依赖需离线导入 |
| 多实例 | 同一 Docker daemon 上多个后端副本，需共享锁目录与 Redis |

### 2.2 交付物

- 容器镜像：backend、frontend、sandbox，多架构（amd64/arm64）；Compose 文件覆盖应用、基础服务、可选浏览器网关 overlay 与环境变量模板。
- 数据库迁移链（Alembic revisions）随镜像发布。
- 安装/升级/回滚/备份恢复脚本、故障手册、版本兼容矩阵（应用 ↔ 数据库 revision ↔ 沙箱镜像）。

### 2.3 依赖清单

| 依赖 | 用途 | 必需 | 说明 |
|---|---|---|---|
| PostgreSQL | 主数据、观测明细、预聚合 | 是 | 16（`postgres:16-alpine`） |
| Redis | cron 抢占、任务注册表、事件日志 | 是 | 7+；事件/注册表可降级 |
| 对象存储 | 工作区、技能包、导出 | 是 | MinIO，S3 兼容 |
| Docker Engine | 沙箱容器执行 | 是 | 挂载 `/var/run/docker.sock` |
| 沙箱镜像 | 工具与代码执行 | 是 | 与后端镜像同源构建 |
| Langfuse | 链路追踪 | 否 | 独立 Compose，外部 PG/Redis/MinIO + ClickHouse |
| RAGFlow / MinerU | 知识库 / 扫描版 PDF | 否 | 后台配置或云服务 token |
| 浏览器 Gateway | 浏览器自动化 | 否 | 独立 overlay，需公网 TLS |

### 2.4 配置与密钥

- 配置来源：`pydantic-settings` 环境变量分组（`DATABASE_`、`REDIS_`、`JWT_`、`AGENT_`、`SANDBOX_`、`STORAGE_`、`LANGFUSE_`、`BROWSER_` 等）；LLM 供应商与模型由管理后台写数据库，不在 `.env`。
- 必须管理的密钥：`JWT_SECRET`（≥32 字符）、对象存储 AK/SK、`BROWSER_SECRET_KEY`（独立随机）、渠道 App Secret、LLM API Key、RAGFlow API Key、MinerU Token、GitHub Token。
- 多环境：dev/staging/prod 使用独立 `.env`、数据库与桶；`SERVER_URL`、`PAGES_BASE_URL`、`CORS_ORIGINS` 按环境设置。

### 2.5 升级与回滚

- 升级内容：应用镜像、沙箱镜像、数据库迁移、配置变更。
- 顺序：备份 → 按 SHA tag 拉取镜像 → 启动触发迁移 → 健康检查 → 冒烟。
- 回滚：镜像退回上一 SHA；数据库若已执行不可逆迁移，只能恢复备份；应用启动自动迁移到 head，旧应用配新库不保证可用（需确认）。

### 2.6 备份恢复

- 备份对象：PostgreSQL（业务表 + 观测明细 + 迁移版本）、MinIO 桶、`.env`/配置、Langfuse 元数据（如启用）。
- RPO/RTO 按客户等级定义；季度至少一次全量恢复到隔离环境，校验登录、对话、文件、定时任务。

### 2.7 运维与容量

- 健康检查：存活/就绪、依赖连通性、迁移状态；日志 stdout 采集、轮转、按 `trace_id` 检索。
- 指标告警：主机、容器、数据库、Redis、对象存储、应用失败率（见 D11）；巡检磁盘/卷、沙箱残留、cron 漏跑、备份、证书。
- 容量：最低/推荐配置、并发会话、沙箱并发、数据库连接数、存储增长。

## 3. 本项目现状

### 3.1 已具备

| 能力 | 实现 |
|---|---|
| 应用编排 | `docker-compose.yml`：`sandbox-image` 预拉取、`backend`、`frontend`，健康检查与依赖顺序 |
| 基础服务 | `docker-compose-base.yml`：PostgreSQL 16、MinIO、Redis 7，独立 Compose 项目与网络 |
| 网络隔离 | 应用与基础服务通过外部网络 `aio-agent-platform-infra` 连接 |
| 沙箱部署 | 后端挂载 Docker socket 与 `sandbox-locks` 卷；`sandbox-build` profile 构建镜像 |
| 前端/网关 | Nginx 静态站点 + `/api` 反代（SSE 不缓冲）；浏览器 overlay 仅绑定 `127.0.0.1:8101` |
| Langfuse | `langfuse/` 独立 Compose，复用外部 PG/Redis/MinIO，本地 ClickHouse |
| 镜像与 CI | GHCR + 阿里云 ACR 多架构 `latest`+`sha`；后端 ruff/mypy/pytest，前端 tsc/lint/build/test |
| 数据库迁移 | `alembic` 39 个 revision；启动 `init_db()` 自动升级，`pg_advisory_lock` 串行化多实例 |
| 迁移保护 | 拒绝未标记版本的旧库；超时 600s 停止启动；历史补丁迁移 |
| 配置模板 | `backend/.env.example` 覆盖数据库、Redis、JWT、Agent、沙箱、存储、Langfuse、RAGFlow、浏览器 |
| 健康检查 | 后端 `/health` 返回服务状态与沙箱活跃数；Compose 每 15s 检查 |
| 数据卷与进程 | 保留 pgdata/minio_data 卷名；supervisor watchdog 防孤儿进程，启动/关闭按依赖顺序清理 |

### 3.2 部分

- **只支持 Docker Compose 单机**：没有 Helm/K8s 清单；镜像支持 arm64，但未验证 ARM 生产部署。
- **多实例能力受限**：后端依赖宿主机 Docker socket 与共享 `SANDBOX_LOCK_DIR`，多副本必须同宿主；采集队列、cron 调度、SSE 连接仍以进程内状态为主。
- **迁移是单向的**：启动自动 `upgrade head`；`c5e6f7a8b9d0` 不提供自动 downgrade，回滚依赖"经过验证的备份恢复方案"，但仓库没有备份工具。
- **Redis 无持久化**：未挂载数据卷；cron occurrence claim（TTL 24h）与任务注册表（TTL 30m）重启后丢失，可能导致漏跑或重复执行窗口。
- **健康检查只有存活**：`/health` 不检查 DB/Redis/对象存储，也没有 readiness；依赖故障时容器仍可能被判健康。
- **密钥明文**：LLM `api_key_encrypted`、渠道 `app_secret_encrypted` 写入处仍是明文（`TODO: encrypt`）；RAGFlow Key 存 `system_config` 明文；无 KMS。
- **日志未接入**：structlog 默认控制台输出，未配置 JSON、`trace_id`、采集器或轮转；`LOG_LEVEL` 只影响 uvicorn 与 SQL echo。
- **CI 只到构建**：没有部署流水线、镜像扫描、SBOM、环境晋级；**离线交付未落地**（无 `docker save` 包与内网脚本）；**容量基线未定义**。

### 3.3 缺失

- Helm Chart、K8s manifests、Operator；应用版本与数据库 revision 的兼容性矩阵、变更日志。
- 备份/恢复脚本、定时备份、恢复演练记录；升级前预检与自动回滚。
- 许可证管理与授权校验；多租户独立部署/独立数据库方案。
- 故障手册、巡检脚本、值班轮换与升级通知模板；离线镜像仓库与内网代理方案。

### 3.4 配置与文件位置

| 关注点 | 文件 |
|---|---|
| 应用/基础服务编排 | `docker-compose.yml`、`docker-compose-base.yml` |
| 浏览器网关 | `docker-compose.browser.yml`、`docs/能力域/D04-工具与外部集成.md` |
| Langfuse | `langfuse/docker-compose-langfuse.yml`、`langfuse/README.md` |
| 镜像与代理 | `backend/Dockerfile`、`frontend/Dockerfile`、`backend/sandbox/Dockerfile`、`frontend/nginx.conf` |
| 配置与启动 | `backend/.env.example`、`core/config.py`、`interface/lifecycle.py`、`db/connection.py` |
| 迁移链 | `backend/alembic/versions/`（head `e7a8192b4c5d`） |

## 4. 关键设计

### 4.1 部署拓扑

```
浏览器 ──TLS──▶ 反向代理/负载均衡（客户提供）
                    ▼
      frontend Nginx :80（宿主 1717）──/api 反代──▶ backend :8100
                                             ├─ PostgreSQL 16 :5435
                                             ├─ Redis 7 :6379
                                             ├─ MinIO :9010 / :9011
                                             └─ Docker socket → 沙箱容器
（可选）browser-gateway 127.0.0.1:8101；（可选）Langfuse 独立项目 :13000
```

- 应用与基础服务是两个 Compose 项目；`docker compose down` 只停应用，不动数据库。
- 生产必须由客户反向代理终止 TLS 并限制来源；打开浏览器网关时仅暴露 `/extension` 与 `/extension/authorize`。

### 4.2 依赖与端口

| 服务 | 容器端口 | 宿主端口 | 说明 |
|---|---|---|---|
| frontend / backend | 80 / 8100 | `${APP_PORT:-1717}` / 未映射 | 仅 frontend 对外，`/api` 反代 backend |
| PostgreSQL | 5432 | 5435 | 生产建议不映射宿主 |
| MinIO | 9000/9001 | 9010/9011 | `STORAGE_ENDPOINT` 需浏览器与后端都可访问 |
| Redis | 6379 | 6379 | 默认无密码，生产必须加 ACL/密码 |
| browser-gateway | 8101 | `127.0.0.1:8101` | 需额外反向代理暴露 |

### 4.3 升级流程

1. **备份**：PostgreSQL 全量 + MinIO 桶清单/关键对象 + 当前 `.env` 与镜像 tag。
2. **预检**：确认目标与当前 revision 路径，检查磁盘、连接数、沙箱残留。
3. **发布**：按 SHA tag 拉取 backend/frontend/sandbox 镜像并 `docker compose up -d`。
4. **迁移**：启动自动加 advisory lock 并 `upgrade head`；失败则启动中止，旧容器仍可用。
5. **验证与观察**：`/health`、登录、对话、工具、文件、定时任务、观测写入；观察 15–30 分钟错误率与延迟，异常则回滚。

### 4.4 回滚与兼容性

- 镜像回滚：切换到上一 SHA tag 重新 `up`；配置回滚：保留上一版 `.env`。
- 数据库回滚：**仅能通过备份恢复**；迁移链不保证 downgrade，历史修复迁移明确不提供自动回滚。
- 因此升级前备份是硬门槛；沙箱镜像应与应用镜像同版本发布，仅升级应用可能造成工具行为不一致。

### 4.5 备份、RPO/RTO

| 对象 | 建议方式 | 建议频率 | 当前状态 |
|---|---|---|---|
| PostgreSQL | 每日全量 + WAL 归档 | 全量日备、WAL 持续 | 缺失 |
| MinIO | `mc mirror` 到备份桶/异地 | 每日 | 缺失 |
| `.env`/配置 | 密钥管理系统版本化 | 每次变更 | 部分（人工保存） |
| Langfuse | 随其 PG/ClickHouse 基础备份 | 每日 | 缺失 |

Redis 可不备份（状态可重建），但需接受 cron claim 与任务注册表丢失后的漏跑窗口。

**建议目标（需与客户确认）**：核心业务库 RPO ≤ 15 分钟，对象存储 RPO ≤ 24 小时；单机故障 RTO ≤ 2 小时，数据恢复 RTO ≤ 4 小时；每季度恢复演练并记录实际 RTO。

### 4.6 密钥管理

- `JWT_SECRET` 未配置或长度不足时应用拒绝启动；轮换会使全部旧 token 失效。
- `BROWSER_SECRET_KEY` 必须独立于 JWT Secret，至少 32 字符。
- 生产建议由 KMS/Vault/云密钥管理注入，容器只读环境变量；镜像层与 `/proc` 不得出现密钥；渠道/模型密钥应加密存储并记录轮换审计。

### 4.7 多实例与横向扩展约束

- 后端与宿主机 Docker daemon 强绑定：多副本必须共享同一 daemon 与同一 `SANDBOX_LOCK_DIR` 卷。
- cron 通过 Redis occurrence claim 防重复，迁移通过 PG advisory lock 串行化；观测队列与部分任务状态为进程内状态，多实例下报表与任务可见性可能不完整（需确认）。
- 未验证前不建议跨主机水平扩展；优先纵向扩容与拆分后台任务。

### 4.8 容量基线

| 项 | 默认值 | 说明 |
|---|---|---|
| 沙箱并发 | 10/进程 | `SANDBOX_MAX_CONCURRENT`，Compose 未透传，取默认 10 |
| 沙箱 CPU/内存 | 1.0 core / 512 MB | 单容器上限 |
| 命令超时/工作区 | 60s / 500 MB | 长任务需调大或拆分 |
| 沙箱空闲回收 | 3600s | 执行中不回收 |
| 后端进程 | 1（无 workers） | `aio-api` 单进程 uvicorn |
| 主机规格 | 需确认 | 仓库无最低/推荐配置说明 |

## 5. 实施建议

### P0（私有化交付的最低门槛）

1. 备份/恢复脚本与定时任务：PostgreSQL 全量 + WAL、MinIO 镜像、配置备份；升级前强制校验最近备份。
2. 发布可回滚：镜像固定 SHA、保留上一版本、升级失败自动/手动回退步骤文档化。
3. 健康检查分层：`/health/live` 与 `/health/ready`，就绪检查 DB/Redis/对象存储与迁移版本；Redis 至少开启 AOF，并把 cron claim 丢失的影响写进运维手册。
4. 密钥加密：模型/渠道/RAGFlow 密钥落库前加密，密钥来源统一；离线交付包（镜像 `save`、依赖清单、内网脚本）。

### P1（可运营）

5. Helm Chart / K8s manifests（含 PVC、探针、资源限额、PDB）；版本兼容矩阵与 CHANGELOG、升级预检脚本。
6. 日志采集、指标接入与告警（对接 D11）。
7. 故障手册与巡检脚本：磁盘、沙箱残留、cron 漏跑、证书、备份。
8. 容量压测与最低/推荐配置表。
9. 多环境晋级流水线（staging → prod）与镜像扫描/SBOM。

### P2（规模化与商业交付）

10. 多租户独立数据库/独立部署方案；许可证管理与授权校验。
11. 灰度升级与双版本并行；跨主机多实例与共享存储方案。
12. 客户侧自服务安装器与一键诊断包。

## 6. 验收标准

- [ ] 客户内网无外网环境，能仅凭离线包完成安装并跑通登录、对话、工具、文件上传。
- [ ] 所有必填环境变量缺失时应用拒绝启动并给出可操作错误；安装有前置检查与版本校验。
- [ ] 任意一次升级前都有可用的数据库与对象存储备份，且备份时间可查。
- [ ] 升级失败可在 30 分钟内回退上一镜像；需要回退数据库时能按演练过的流程恢复。
- [ ] `/health/ready` 能反映数据库、Redis、对象存储和迁移状态，依赖故障时不误报健康。
- [ ] 有明确的 RPO/RTO 文档，并完成至少一次恢复演练。
- [ ] 密钥不出现在镜像、仓库与日志中；模型/渠道密钥加密存储。
- [ ] 多实例部署时 cron 不重复执行、迁移不并发冲突；限制条件写入文档。
- [ ] 有版本兼容矩阵、CHANGELOG、故障手册、巡检脚本、最低/推荐配置与扩容指引，并经过压测验证。
- [ ] 日志可集中采集并按 `trace_id` 检索，保留期满足客户要求。
