> 合并说明：本文由 2 份原始文档合并，内容保持原样，仅调整标题层级。

## 定时任务结果与通知

定时任务的执行结果和 IM 通知分别处理。智能体负责判断业务条件、上报摘要及通知决策；执行器在运行结束后统一投递。静默表示不发送飞书等 IM 消息，后台仍保存摘要、工具调用和静默原因。邮件属于任务自身的工具行为，不受 IM 通知决策控制。

参考 OpenClaw 的 [自动投递与静默信号](https://docs.openclaw.ai/cli/cron#silent-token-suppression) 和 [Heartbeat 结构化通知决策](https://docs.openclaw.ai/gateway/heartbeat#response-contract)，本项目采用以下契约。

### 执行模型

新建、编辑定时任务可选择独立的执行模型，任务卡片显示当前选择。模型优先级为任务 `model_id` → 智能体模型 → 租户默认模型。清空任务模型恢复跟随智能体，修改从下次执行生效，手动执行和自动调度使用同一规则。

创建接口支持 `model_id`；更新时省略该字段保留原值，传 UUID 更换模型，传 `null` 清除覆盖。`create_cron_job` 工具也支持该参数。任务的模型配置参与创建幂等与重复配置比较。

AI 可先调用只读工具 `list_models` 查询当前执行租户的可选模型，返回 `id`、`name`、`model_name`、`provider`、`is_default`、`is_multimodal`，然后将返回的 `id` 传入 `create_cron_job.model_id`。无可选模型时返回空列表；不暴露密钥或连接地址，也不探测上游推理。工具按执行上下文解析租户并重新校验用户及成员资格，不跟随界面切换租户。前端模型列表、AI 查询和定时任务指定模型校验复用相同可用性条件。

显式指定的模型及其提供商必须启用且属于任务租户；执行前再次校验，失效时记录执行失败，不静默换用默认模型。生成的运行会话保留该模型覆盖，不修改智能体本身。历史任务 `model_id` 为 `null`，保持原行为。Alembic 迁移 `b4d5e6f7a8b9` 和启动幂等迁移同步新增可空列。

### 提示词组织

定时任务入口在默认或自定义角色、记忆等系统提示之后统一追加 `backend/prompts/cron_execution.j2`，普通聊天不会加载这段运行协议。模板区分是否绑定 IM 渠道，依次说明执行证据、通知决策、结构化上报和兼容回退：

- 明确区分条件满足、已确认未满足、数据不足或执行异常，不能将无法判断写成未触发。
- 先按任务完成邮件等操作，再上报结果；IM 静默与邮件各自遵守约定。
- 明确静默条件得到证实时使用 `notify=false`；异常按任务错误通知规则处理，未明确允许异常静默时通知。
- `cron_respond` 是主要结果协议；成功只表示已登记，不能声称已送达或再重复发送。`NO_REPLY` 仅作为尚未完成结构化上报时的兼容回退。

工具 schema 聚焦参数和登记语义；`create_cron_job.message` 的描述要求保留独立、完整的任务条件，分别写清 IM 通知与邮件动作。已有任务的 message、智能体自定义提示和历史记忆不会被批量改写。

### 结果协议

每次执行提供 `cron_respond` 工具。该工具只登记结果，不立即发送消息。

```json
{
  "notify": false,
  "summary": "恒生科技ETF：现价低于 MA60，量比不足，两个条件均未满足。",
  "reason": "右侧信号未触发"
}
```

- `notify` 必须为布尔值。
- `summary` 必须是非空执行摘要，保存在 `CronJobRun.output`。
- `notify=false` 时必须填写非空 `reason`；后端跳过渠道发送，记录主动静默。
- `notify=true` 时发送 `notification_text`，省略时发送 `summary`。
- 多次有效上报以最后一次为准；非法参数不会覆盖已有决策。
- 工具返回“已登记”不代表消息已发出。只有执行完成后，执行器才会调用渠道发送函数。

未调用 `cron_respond` 时：

1. 有渠道且最终回答非空：默认投递最终回答，漏调工具不会被当作静默。
2. 最终回答去除首尾空白后严格等于大写 `NO_REPLY`：主动静默。
3. 空输出且无有效结果上报：执行失败，不能当作主动静默。
4. 未绑定渠道：结果只保存在后台。

`NO_REPLY.`、小写 `no_reply`、代码块、JSON、附带解释的 `NO_REPLY` 均作为普通正文处理。优先使用结构化协议，以保留完整摘要及静默原因。结构化决策优先于最终回答中的控制信号，发送层不根据“保持静默”“未发送邮件”等自然语言猜测通知意图。

旧提示词调用 `notify_channel` 时仅登记候选正文，不立即发送。结构化决策优先；没有结构化决策时，最终 `NO_REPLY` 仍能抑制旧通知请求。一个运行最多调用一次渠道发送函数。

### 执行与投递状态

`status` 继续表示执行状态：`running` / `success` / `failed`。新增字段与它独立：

| 字段 | 含义 |
| --- | --- |
| `delivery_status` | `pending` 待处理、`sent` 渠道确认发送、`suppressed` 主动静默、`not_requested` 未请求、`failed` 明确未成功、`unknown` 无法确认 |
| `delivery_reason` | 静默原因，或 `silent_token` / `no_channel` / `execution_failed` |
| `delivery_error` | 渠道投递错误，不覆盖执行错误 |

发送前先持久化 `unknown`，防止进程在外部 IO 中断时留下虚假的成功记录。发送函数明确返回未成功时记录 `failed`；异常或发送中取消时保留 `unknown`，不盲目重试。任务已生成有效结果而发送失败，不把执行状态改成失败。

生成过程抛错或取消时，即使先前已登记通知，也不会发送该候选结果。运行结束会清理 ContextVar 并关闭上下文；继承上下文的延迟子任务也不能在运行结束后修改决策。工具处理器还会核对用户和会话，避免跨运行写入。

管理页面的运行记录分别展示执行状态和通知状态，悬停通知标签可查看静默原因或发送错误。
单任务记录弹窗和全部执行记录页使用相同的通知状态展示，详情抽屉直接显示静默原因或发送错误。

### 边界

框架执行显式的通知决策，不会自行计算股票信号或推断业务真伪。若模型错误上报 `notify=true`，仍会推送；如需确定性业务规则，应由行情计算代码产出经过校验的结构化条件。任务应明确写出哪些条件允许静默，默认仍通知。

此协议只管理定时任务结果的 IM 推送，不撤销已经由其他外部工具执行的邮件等副作用。工具白名单仍按任务所属智能体过滤，并额外提供结果上报工具。

### 升级与验证

增加 Alembic 迁移 `a3c4d5e6f7b8`，启动时的幂等列迁移同步添加三个投递字段。历史记录标为 `unknown`，不根据执行成功推断曾经发过通知，不更改历史租户归属或任务提示词。生产升级需部署新版本及应用 schema 变更；本次开发不直接连接远程数据库迁移。

自动化回归覆盖默认投递、显式静默保留摘要、独立通知正文、精确控制信号、旧工具兼容、推送失败与不确定结果、异常与取消、上下文隔离及 API 字段。真实渠道收到消息属于单独的部署验证。

### 实测发现并修复

1. 第一轮完整启动发现权限白名单将 Tool 对象当作字符串集合处理，触发 `TypeError: unhashable type: Tool`。改为从实际工具 schema 提取名称，也覆盖 MCP 等 schema 工具；结果工具以真实 Tool 对象进入系统提示词。回归保留真实内置工具列表、实际 AgentLoop 和 ToolExecutor，避免空工具替身掩盖类型问题。初次失败记录保留，修复后重新执行通过。
2. 全部执行记录页此前没有展示通知状态。抽取共享 CronDeliveryStatus 组件，统一单任务弹窗、全量列表和详情抽屉。
