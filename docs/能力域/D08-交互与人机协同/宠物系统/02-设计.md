## 宠物任务条 SSE 实时推送技术方案

> 日期：2026-08-03
> 前置文档：《需求》第一部分（宠物系统基础）、《需求》第二部分
> 目的：把宠物任务条的状态同步从「前端 5s 轮询 `GET /api/pets/active-tasks`」改为「用户级 SSE 长连接推送」，让渠道（飞书等）触发的 Agent 任务状态（开始/工具切换/完成）实时到达前端，消除轮询粒度带来的延迟。

### 1. 背景与动机

现状：

- 飞书等渠道触发的 AgentLoop 完全跑在后端，浏览器没有任何 SSE 连接，宠物 widget 只能靠 `setInterval` 每 5s 轮询一次 `GET /api/pets/active-tasks` 感知状态（`PetWidget.tsx`）。
- 任务状态由 `channels/pipeline.py` 通过 `task_started / task_tool / task_finished` 写入 Redis 哈希 `aio:pet_tasks:{user_id}`（`core/task_registry.py`），宠物路由轮询读出。

问题：

- **轮询粒度延迟**：任务出现、工具名切换、任务完成消失，最多滞后 5s（一次轮询周期）。
- 页面切后台时轮询暂停（`document.visibilityState` 守卫），切回来前状态完全盲区。
- 每次轮询都是一次完整 HTTP 往返 + Redis `hgetall`，无事件时纯浪费。

目标：

- 任务开始/工具切换/完成三类事件**即时**到达前端（亚秒级）。
- 后台标签页依然能收到事件（SSE 网络事件不受 timer throttle 影响）。
- 连接建立即同步当前全量快照，断线重连后自动恢复，不丢状态。
- Redis 故障、连接中断等异常时**优雅降级**，不拖垮对话链路（沿用宠物附属系统定位）。

### 2. 总体设计

```
渠道(飞书) webhook
      │  InboundEvent
      ▼
channels/pipeline.py  ── task_started / task_tool / task_finished ──┐
      │                                                             │
      │ 写入 Redis hash (aio:pet_tasks:{user_id})                   │ 发布到 Redis 频道
      │                                                             ▼
      │                                          aio:pet_task_events  (Redis Pub/Sub, 单频道)
      │                                                             │ 订阅 + 按 user_id 过滤
      │                                                             ▼
      │                                          core/task_events.py TaskEventBroker
      │                                                             │  内存注册表 user_id → set[Queue]
      │                                                             ▼
      │                                             SSE 端点 GET /api/pets/tasks/events
      │                                                             │  连接即快照 + 增量事件 + 心跳
      │                                                             ▼
      │                                           前端 petsApi.watchActiveTasks (fetch 流)
      │                                                             ▼
      │                                           petStore.applyRemoteTaskEvent / syncRemoteTasks
      │                                                             ▼
      │                                           宠物 widget 任务条 (tasks map)
```

要点：

- **发布端**：`task_registry` 是任务生命周期的唯一写入口，在其三个函数末尾发布事件，`pipeline.py` 零改动。
- **订阅端**：`TaskEventBroker` 每进程一个共享 Redis pubsub 订阅后台任务，按 `user_id` 分发到各 SSE 连接的内存队列。
- **单频道 + payload 带 user_id**：避免「每用户一条频道」导致的频道数量爆炸；多 worker 各自订阅同一频道即可广播。
- **先订阅后快照**：规避「快照读取与增量事件之间丢事件」的竞态。

### 3. 事件协议

SSE 传输沿用 chat 流既有约定：`data: {json}\n\n`（单行 JSON，事件类型放 `type` 字段），复用 `chat.py` 的 `_sse_event`。不写命名 `event:` 字段。心跳为 SSE 注释行 `: ping\n\n`（前端解析器对 `:` 开头的行天然跳过）。

| type | 方向 | 说明 |
|---|---|---|
| `pet_task_snapshot` | 连接建立时 | 当前在跑任务全量快照，`tasks` 为 `PetActiveTask[]` |
| `pet_task_started` | 任务开始 | `task` 为完整任务对象 |
| `pet_task_tool` | 工具切换 | `session_id` + `tool` 名 |
| `pet_task_finished` | 任务结束 | `session_id`，前端打勾停留后移除 |

payload 示例：

```json
// 连接时（先于任何增量事件）
{"type": "pet_task_snapshot", "tasks": [
  {"session_id": "…", "label": "查一下天气", "tool": null,
   "source": "feishu", "chat_key": "…", "agent_id": "…", "started_at": 1754…}
]}

// 增量
{"type": "pet_task_started", "task": { /* 同 snapshot 元素 */ }}
{"type": "pet_task_tool", "session_id": "…", "tool": "web_search"}
{"type": "pet_task_finished", "session_id": "…"}
```

`task` 对象字段与 `PetActiveTask`（`frontend/src/lib/types.ts`）完全一致，前端可复用现有合并逻辑。

### 4. 后端设计

#### 4.1 `core/task_registry.py` — 发布事件

- 新增 `_publish(user_id, event: dict)`：`_redis().publish("aio:pet_task_events", json.dumps(event))`，try/except 静默降级（沿用模块既有模式：Redis 不可用不拖垮对话）。
- 在 `task_started` / `task_tool` / `task_finished` 的 **Redis 写入之后**各发布一次，保证「订阅方收到的事件」与「快照读到的状态」一致。
- 复用现有 `_redis()` 懒加载单例。

#### 4.2 新模块 `core/task_events.py` — 订阅端 broker

`TaskEventBroker` 单例：

| 成员 | 说明 |
|---|---|
| `_subscribers: dict[str, set[asyncio.Queue]]` | user_id → 该用户的所有 SSE 连接队列 |
| `_listen_task: asyncio.Task \| None` | 共享 Redis pubsub 订阅后台任务，首次 `subscribe` 时懒启动 |
| `_listen_loop()` | 订阅 `aio:pet_task_events`，每条消息按 `user_id` 过滤，`put_nowait` 写队列（满则丢）；连接异常带 1s 退避重连 |
| `stream(user_id)` | async generator：先订阅 → `task_registry.list_tasks` 读快照 → 循环 `wait_for(q.get(), timeout=25)`（超时产出心跳哨兵）→ `finally` 退订 |

#### 4.3 `interface/routes/pets.py` — SSE 端点

- `GET /api/pets/tasks/events`，依赖 `user: CurrentUser`（HTTPBearer header）。
- 返回 `StreamingResponse(media_type="text/event-stream", headers={"Cache-Control": "no-cache", "Connection": "keep-alive", "X-Accel-Buffering": "no"})`。
- 遍历 `broker.stream(user.id)`：dict → `_sse_event(dict)`；心跳哨兵 → `: ping\n\n`。
- 保留 `GET /active-tasks` 轮询端点（调试/回退用），前端不再调用。

### 5. 前端设计

#### 5.1 `lib/api.ts` — `petsApi.watchActiveTasks(onEvent)`

- 复用 `stream()`（L252-341）的 fetch `getReader()` + `\n\n` 切块 + `data: ` 前缀解析骨架，GET `/pets/tasks/events` + `Authorization: Bearer` header。
- 返回 `close: () => void`（内部 `AbortController.abort()`）。

#### 5.2 `stores/petStore.ts` — 远端事件处理

- 从 `syncRemoteTasks` 的 incoming 分支抽出 `mergeIncoming(tasks, t: PetActiveTask)` helper，快照与增量复用。
- 新增 `applyRemoteTaskEvent(ev)`：

| 事件 | 处理 |
|---|---|
| `pet_task_snapshot` | 调 `syncRemoteTasks(ev.tasks)`（全量合并，天然兼容现有逻辑） |
| `pet_task_started` | `mergeIncoming` 单条 upsert |
| `pet_task_tool` | 按 `session_id` 更新 `tool` + `updatedAt` |
| `pet_task_finished` | `markDone` + `scheduleRemoval`（保留 60s 打勾停留） |

#### 5.3 `components/pet/PetWidget.tsx` — 轮询改 SSE

- 替换 L185-204 的 `setInterval` 轮询：`useEffect` 里 `petsApi.watchActiveTasks(...)`，事件喂给 store，cleanup 调 close。
- 连接 error/意外断开 → 3s 后重连（简单退避）。
- `effectiveMood` 工作态推导（L405-409）不变，任务仍在同一 `tasks` map；本地 web 聊天任务（走 chat SSE → `reportEvent`）不冲突。

### 6. 时序图

```
浏览器               broker/SSE 端点          Redis 频道            渠道 pipeline
  │  GET /tasks/events │                       │                       │
  │──────────────────▶│  subscribe(user_id)    │                       │
  │                   │───────────────────────▶│                       │
  │                   │  list_tasks 读快照     │                       │
  │                   │◀───────────────────────│                       │
  │◀── snapshot ──────│                       │                       │
  │                   │                       │   task_started 发布    │
  │                   │                       │◀──────────────────────│
  │                   │◀─ msg(user_id) 过滤 ──│                       │
  │◀── started ───────│                       │                       │
  │                   │                       │   task_tool 发布       │
  │                   │◀──────────────────────│                       │
  │◀── tool ──────────│                       │                       │
  │                   │                       │   task_finished 发布   │
  │                   │◀──────────────────────│                       │
  │◀── finished ──────│                       │                       │
  │◀── : ping ────────│  (每 25s 心跳)        │                       │
```

### 7. 降级矩阵

| 故障场景 | 表现 | 兜底 |
|---|---|---|
| Redis 不可用（发布侧） | 事件静默丢弃 | 对话链路不受影响（沿用现有 try/except） |
| Redis 不可用（订阅侧） | pubsub 订阅失败/断连 | 监听循环 1s 退避重连；SSE 仍可建立、只发快照不发增量 |
| 浏览器断连 | 生成器抛 CancelledError | `finally` 退订队列，不泄漏 |
| 连接中途网络抖动 | 前端读到 EOF/error | 3s 后重连，重建即收快照恢复状态 |
| 快照与增量之间丢事件 | 任务状态短暂缺一条 | 快照+增量幂等合并；任务残留由 TTL(30min)/前端 60s 清扫兜底 |
| 多 worker 部署 | 各 worker 独立订阅同一频道 | 频道广播天然覆盖所有浏览器连接 |

### 8. 非功能需求

- **认证**：`CurrentUser`（HTTPBearer），SSE 长连接只在建立时校验一次 token（与现有 chat SSE 一致，长连接期间 token 过期不断连）。
- **用户隔离**：broker 按 `user_id` 过滤分发，事件只到达属主连接。
- **心跳**：每 25s 发 `: ping` 注释行，维持代理连接活性。
- **连接规模**：每浏览器 tab 一条常驻 SSE，队列长度有界（满则丢），内存可控。
- **性能**：无事件时零业务流量；事件到达到亚秒级。

### 9. 验收标准

1. 渠道（飞书等）消息发出后，宠物任务条**即时**出现任务 pill（无需等待 5s 轮询）。
2. 任务调用工具时，pill 上的工具名**即时**切换。
3. 任务结束，pill **即时**打勾，60s 后移除。
4. 页面在后台标签页时，任务状态仍能更新。
5. 断网重连后，任务条状态通过快照自动恢复。
6. 本地 web 聊天任务条行为不变（回归）。
7. Redis 停止时，Web 聊天不受影响；SSE 只退化为快照态（可接受的降级）。

## 宠物动作系统与智能体控制方案

> 日期：2026-08-04
> 前置文档：《需求》第一部分（宠物系统基础）、《需求》第二部分（绑定模型与人设合成）
> 目的：在"宠物绑定智能体"基础上，让智能体不仅能说，还能**主动控制宠物的动作**（动画）。同时把"动作"从精灵图行号升级为**有名字的一等实体**——上传者可改包级动作名，领养者可在自己宠物上覆盖改名。

### 1. 背景与动机

现状（P0 已上线 / 已规划）：

- 宠物动作 = 精灵图的一行（一个动画），通过 `pet_packages.row_mapping`（状态→行）驱动状态机；互动播放直接按行号操作。
- 动作的展示名是前端推导的：`rowName(pkg, row)` = 状态名反查 → Codex 标准行名 → 「动画 N」。**名字只读、不可改，且分散在前端逻辑里。**
- 《需求》第二部分 里，绑定 Agent 后智能体只生成**气泡文本**，动作仍由前端写死（点击固定播 happy 行）。**智能体动嘴不动手。**

用户确认的两个动作控制时机：

1. **左键点击宠物** → 智能气泡：Agent 生成一句话的同时，**自己挑一个动作让宠物演出来**（开心说"主人你好呀"就挥手，被戳就缩一下）。
2. **右键 → 和 TA 聊聊** → 宠物闲聊：Agent 在对话过程中**随时主动触发动作**（"我想你了"时跳一跳，问完问题歪头思考）。

目标：

- 绑定 Agent 后，两个交互时机的动作由 Agent 决定，不再前端写死。
- 动作拥有**名称**，作为展示名 + 智能体寻址的词汇表。
- **上传者**（包创建人/管理员）可修改**包级**动作名，影响所有未自定义的领养者。
- **领养者**（宠物拥有者）可在**实例级**覆盖动作名，只影响自己的宠物；改完即时生效，也是给智能体的个性化词汇表。
- 未绑定 / 动作名无效 / LLM 失败全部静默降级，宠物渲染与聊天主流程零影响（沿用既有隔离原则）。

### 2. 核心概念

#### 2.1 动作 = 精灵图的一行（动画）

动作有三个属性：

| 属性 | 说明 | 可变性 |
|---|---|---|
| `row` | 精灵图行号 | **不可变**，动作的唯一身份（行由精灵图物理结构决定） |
| `name` | 动作名称（展示 + 智能体寻址） | 可编辑，两级覆盖 |
| `state` | 平台状态（可选，`idle/work/think/...`） | 包级只读（来自 row_mapping） |

动作身份用 `row`（物理行）而非 `name`：改名不影响状态机与历史数据，实例覆盖在包改名/换版本后依然锚定同一行。

#### 2.2 动作目录（两级，实例优先）

| 层级 | 字段 | 谁设置 | 作用 |
|---|---|---|---|
| 包级（动作目录） | `pet_packages.actions`（JSONB，`{row: {name, state}}`） | 上传者 / 管理员 | 包的"出厂动作名"，上传时自动生成，创建人可改 |
| 实例级（改名覆盖） | `user_pets.action_aliases`（JSONB，`{row: name}`） | 宠物拥有者 | 个人改名，**优先级高于包级** |

**名称解析顺序**（展示名 + 智能体寻址共用同一链路，后端单点解析）：

```
user_pets.action_aliases[row]  →  pet_packages.actions[row].name  →  row_mapping 反查状态名
                                    →  Codex 标准行名（CODEX_ROW_NAMES）  →  「动画 N」（占位）
```

- 名字**去重校验**：同一目录内不允许两个动作同名（否则 name→row 寻址歧义），保存时拒绝并提示。
- 实例覆盖存 `row` 为 key，包后续改名/更新不影响用户自定义；覆盖值解析后仍参与去重校验（对当前用户）。
- 包被删除/下架不回收已领养用户的动作数据（沿用 4.6 既有规则）。

#### 2.3 智能体的动作词汇表

绑定 Agent 后，智能体**只能从当前宠物解析出的动作名中选择**，不能自创：

- 词汇表 = 目录中**解析名非「动画 N」占位符**的动作（占位符对 Agent 无语义，排除）。
- 数量上限 12 个（按 state 映射在前 → Codex 命名 → 用户自定义排序截取），控制 prompt 成本。
- 用户给动作改了有意义的名字后，该动作自动进入智能体词汇表——**改名字 = 给智能体加戏**。
- 未绑定 / 词汇表为空：智能体不控制动作，行为与现状一致。

### 3. 功能需求

#### 3.1 动作名称管理（P0）

- **上传者**：「我的上传」包卡片 → 「动作名称」入口，打开动作目录弹窗，逐行改名（行缩略图预览 + 当前名 + 输入框）。仅创建人/管理员可改。
- **领养者**：「我的宠物」宠物卡片 → 「动作名称」入口，同样弹窗逐行改名；提供「重置为包级默认」一键清空实例覆盖。
- 改名即时生效：右键菜单、气泡动作、闲聊智能体词汇表同步更新（前端重新拉取 active 响应）。
- 校验：row 越界拒绝；name 非空、≤ 20 字、目录内唯一；空名等于恢复默认（删除该条覆盖）。

#### 3.2 左键点击 → 智能气泡动作联动（P0）

触发沿用现有交互（左键点击）。已绑定 Agent 时：

1. 前端点击 → `POST /api/pets/{user_pet_id}/bubble`。
2. 后端合成人设 prompt（见 2.3 节 + 动作词汇表），单轮调 LLM，结构化输出 `{"text": "...", "action": "<动作名>|null"}`。
3. 后端**先** yield `pet_action:{name}` 事件，**再**逐字 yield `text_delta:`。
4. 前端收到 `pet_action:` → name→row → 播放对应动画；`text_delta:` → 打字机上屏气泡。
5. Agent 未返回 action / 动作无效 → 播放默认 happy 行（现状），文本照常展示。
6. 未绑定 / 不可见 / 超限 / 失败 → 现有 fallback：静态气泡 + happy 行（现状）。

#### 3.3 右键 → 和 TA 聊聊 → 动作联动（P0）

- 在 《需求》第二部分 3.3 闲聊会话的 AgentLoop 中，白名单工具新增 **`pet_action`** direct handler：

  ```
  pet_action(name: string)  // 让宠物播放指定动作动画；name 必须是当前宠物可用动作名之一
  ```

- 实现：`tool_executor.register_direct_handler('pet_action', ...)` → handler 内解析 name→row → push `{"type": "pet_action", "name", "row"}` 到 `event_queue` → SSE drain 转发（与 AskUserQuestion / delegation 同机制，《需求》第二部分 5.3 链路零改动）。
- **与状态机的关系**：`pet_action` 播放一次性"情绪动作"（挥手/跳跃/自定义），播完回状态机驱动状态（think/work/celebrate 联动不变）；不覆盖状态机正在播的状态动画，两者串行不打架。
- 降级：
  - name 解析失败 → 返回错误给 Agent（"动作「X」不存在，可选：...，请重试"），不 crash、不中断对话；
  - 未绑定 → 不注册该工具，Agent 无法触发动作；
  - 用户改名后 Agent 按旧名调用 → 同上返回当前词汇表引导重试。

#### 3.4 SSE 协议新增事件

聊天与气泡共用一种新事件类型：

```
data: {"type": "pet_action", "name": "挥手", "row": 3}
```

- 气泡模式：由 bubble 接口直接 yield（`text_delta` 之前）。
- 闲聊模式：由 `pet_action` handler 经 `event_queue` 转发。
- 前端 `petStore` 统一监听 → `playRow(row)`，与现有 `actionRow` 播放通道复用。

### 4. 数据模型变更

| 表 | 变更 | 说明 |
|---|---|---|
| `pet_packages` | + `actions JSONB NULL` | 动作目录 `{row: {name, state}}`，上传时自动生成（见 5.1），创建人可改 |
| `user_pets` | + `action_aliases JSONB NULL` | 实例级改名覆盖 `{row: name}`，拥有者可改 |

均无外键约束（沿用项目惯例）。`row_mapping`（状态→行，驱动状态机）**不变**；`actions`（行→名，展示/寻址）与之共享 `state`，不重复存储状态逻辑。

### 5. 后端设计

#### 5.1 动作目录自动生成（上传时）

`build_actions(pkg, row_mapping, row_count)`：

- 对每行 `row`：`name =` 状态名（row_mapping 反查该行的 state）→ Codex 标准行名 → 「动画 N」；`state =` row_mapping 指向该行的 state（无则 null）。
- 存 `pet_packages.actions`。`row_mapping` 的 `_row_frames` 等附加字段不进入 actions。
- 兼容旧数据：`actions` 为空时前端解析回退到现有 `rowName()` 推导逻辑（迁移前不破坏现状）。

#### 5.2 名称解析（后端单点）

`resolve_actions(user_pet, pkg)`：

```
for row in range(pkg.row_count):
    name = user_pet.action_aliases.get(row) or pkg.actions[row].name or state_label or codex_name or f"动画 {row}"
```

返回 `[{row, name, state}]` 列表 + `agent_vocab`（解析名非占位符、去重、截断 12 的 name 列表）。`GET /api/pets/active`、bubble、chat 工具校验三处复用。

#### 5.3 接口

| 接口 | 说明 |
|---|---|
| `PUT /api/pets/packages/{id}/actions` | 上传者改包级动作名：`{actions: [{row, name}]}`；仅创建人/管理员；校验 row 范围、name ≤ 20 字、目录内唯一 |
| `PUT /api/pets/{user_pet_id}/actions` | 领养者改实例级动作名：`{aliases: {row: name}}`；空 value 删除该条覆盖；`{}` 清空全部恢复包级 |
| `GET /api/pets/active` | 响应扩展：`actions`（解析后的动作列表 `[{row, name, state}]`，含实例覆盖生效后的最终名） |
| `POST /api/pets/{user_pet_id}/bubble` | 扩展：成功时先发 `pet_action` 事件再流式 `text_delta`；fallback 响应 `{fallback: true, action: null, text}`（前端播 happy 行） |
| （闲聊） | 白名单新增 `pet_action` direct handler；SSE 新增 `pet_action` 事件 |

#### 5.4 气泡动作约束 prompt 模板（追加到 《需求》第二部分 2.3 人设合成之后）

```
可用动作（只从这些里选）：{agent_vocab}。
回复 JSON：{"text": "一句话，不超过{N}字，宠物口吻", "action": "<与文本情绪匹配的动作名，或 null>"}。
开心→选开心类动作；难过→选沮丧类动作；拿不准→null（默认动画）。
```

- `max_tokens ≤ 80`、无工具、无历史（沿用 《需求》第二部分 5.3 气泡链路），动作词汇表约 12 个短名，输入成本可忽略。
- 结构化输出解析失败（LLM 未按 JSON）→ 视作 `{text: 原始输出, action: null}`，仍降级为默认动画。

#### 5.5 闲聊 `pet_action` 工具

- 注册：`tool_executor.register_direct_handler('pet_action', handler)`，仅当解析出绑定 Agent 且词汇表非空时注册。
- handler 签名：`(name: str) -> str`；name→row 走 `resolve_actions` 反查，命中 push `pet_action` 事件并返回 `ok`，未命中返回纠正信息。
- 事件推送与 SSE：`{"type": "pet_action", "name": ..., "row": ...}` 经 `event_queue` → 聊天路由 drain 循环 `_sse_event()` 转发（chat.py:1082 既有逻辑，零改动）。
- 不写会话消息、不记 token（动作是渲染指令，非用户可见内容）。

#### 5.6 降级矩阵（在 《需求》第二部分 5.4 基础上新增）

| 场景 | 行为 |
|---|---|
| 未绑定 / 词汇表为空 | 点击 → 静态气泡 + happy 行（现状）；闲聊无 `pet_action` 工具 |
| Agent 未返回 action / 动作无效 | 气泡播默认 happy 行，文本照常；闲聊工具返回纠正信息，对话不中断 |
| 用户改名后 Agent 按旧名调用 | 校验失败 → 返回当前词汇表引导重试 |
| 动作目录解析失败（脏数据） | 回退前端 `rowName()` 推导逻辑，不报错 |

### 6. 前端设计

- `petStore`：
  - `actions`：解析后的动作目录（`GET /api/pets/active` 返回，缓存随 activePet 加载）。
  - `playAction(name)`：name→row → `playRow(row)`。
  - `bubbleStream`：气泡流式累积状态；`pet_action` 事件先触发动画再累积文本；3s 无首个 token 回退静态。
  - `rowName(pkg, row)` 重构：优先用目录解析名，目录缺失回退现有推导。
- `PetWidget`：
  - 左键点击：绑定且配额内 → 调 bubble 接口（处理 `pet_action` + `text_delta`）；否则现状静态气泡 + happy 行。
  - 右键「播放动画」子菜单：label 改用动作目录解析名（行号保留在 key 里），不再前端推导。
  - 右键菜单新增「动作名称」入口 → 跳宠物页对应卡片。
  - 闲聊中监听 `pet_action` SSE 事件 → `playAction(name)`。
- `PetsPage`：
  - 「我的上传」包卡片：动作名称编辑弹窗（行缩略图 + 输入框，保存 `PUT packages/{id}/actions`）。
  - 「我的宠物」宠物卡片：动作名称编辑弹窗 + 「重置为包级默认」。
- `types.ts` / `api.ts`：`PetAction {row, name, state}`、`updatePackageActions()`、`updatePetActions()`。
- 无 Agent 绑定 / 未启用宠物智能互动时，UI 不出现动作名称入口的智能体相关文案（沿用 《需求》第二部分 前端开关逻辑）。

### 7. 权限与隔离

- 包级动作名：仅创建人/管理员可改（复用 `_get_owned_package`）；改名不影响已领养用户（沿用 4.6：包改动不回收领养数据）。
- 实例级动作名：仅宠物拥有者可改（复用 `user_pets.user_id` 校验）。
- 智能体寻址动作名：仅限当前用户可见宠物的动作，词汇表来自 `resolve_actions`（跨租户不可触达）。
- 气泡单轮无工具、无历史，动作名经 sanitize 后仅作寻址 key，无注入面；`pet_action` 是 direct handler，不接沙箱/外部工具。

### 8. 成本与性能

- 气泡：动作词汇表（≤12 短名）进 prompt，结构化输出仍受 `max_tokens ≤ 80` 约束；配额沿用 `pet_exp_logs reason='bubble_llm'` 当日计数，不新增计费项。
- 闲聊：`pet_action` 为本地 direct handler，无 LLM 往返、无外部调用，成本可忽略；`max_iterations ≤ 3` 不变。
- 名称解析为纯内存计算（`row_count` 小），无新增 DB 查询热点。

### 9. 分期计划

| 阶段 | 内容 |
|---|---|
| P0 | `actions` / `action_aliases` 数据模型与接口、上传时自动生成动作目录、包级/实例级改名前端、气泡动作联动（`pet_action` 事件 + 结构化输出） |
| P0.5 | 闲聊 `pet_action` direct handler + SSE 转发 + 前端聊天动作联动 |
| P1 | 动作名与文本情绪匹配的模型侧优化（prompt 示例注入）、改名冲突提示优化、任务播报（《需求》第二部分 3.4）带动作 |
| P2（待定） | 动作名收藏/排序、跨包动作名移植、飞书渠道宠物动作 |

### 10. 验收标准

1. 绑定 Agent 后左键点击宠物：气泡为该 Agent 生成的一句话，且播放与文本匹配的动作动画；Agent 未指定动作时播放默认开心动画。
2. 绑定 Agent 后右键「和 TA 聊聊」：Agent 可在对话中通过动作名让宠物播放指定动画（前端可见动画切换）；未知动作名不报错、Agent 收到纠正引导。
3. 上传者修改包级动作名后：新领养者菜单显示新名；未自定义的已领养用户同步看到新名。
4. 领养者修改实例动作名后：右键菜单显示新名，闲聊中智能体可寻址新名；重置后恢复包级名。
5. 动作名保存时越界/空/重复被拒绝并提示；删除/下架包不影响已领养用户的动作数据。
6. LLM 全挂或未绑定时：点击出静态气泡 + 默认动画，聊天主流程无任何异常（回归 《需求》第二部分 验收 6）。

### 2. 宠物绑定智能体设计（对应 02 需求）

#### 2.1 数据表变更

| 表 | 变更 | 说明 |
|---|---|---|
| `pet_packages` | + `default_agent_id UUID NULL` | 包级默认人设 Agent |
| `user_pets` | + `agent_id UUID NULL` | 实例级绑定 |
| `conversations` | + `source VARCHAR(16) DEFAULT 'chat'`（取值 `chat` / `pet`） | 区分宠物闲聊会话；已有多渠道接入若已有等价字段则复用 |
| `token_usage_daily` | source 新增 `pet_bubble` / `pet_chat` | 成本归集 |

均无外键约束（沿用项目惯例，应用层维护关系 + 实时可见性校验）。

#### 2.2 接口

| 接口 | 说明 |
|---|---|
| `PUT /api/pets/{user_pet_id}/agent` | 实例级绑定/解绑（body: `{agent_id: UUID \| null}`；校验 Agent 对当前用户可见） |
| `PUT /api/pets/packages/{id}/default-agent` | 包级默认人设（仅包创建人/管理员；校验 Agent 对创建人可见） |
| `POST /api/pets/{user_pet_id}/bubble` | 智能气泡（SSE 流式返回 `text_delta`；未绑定/超限/失败时回退响应 `{fallback: true, text: "..."}`，前端直接展示静态文案） |
| `POST /api/pets/{user_pet_id}/chat` | 开启/复用宠物闲聊会话，返回 `conversation_id`；之后走现有会话消息接口 + SSE |
| `GET /api/pets/active` | 响应扩展：`agent`（解析后的绑定 Agent 简要信息：id/name/icon + 生效层级 instance/package） |

#### 2.3 执行链路

**气泡（bubble）**：不走 `AgentLoop`——单轮、无工具、无历史，直接调 LLM client（合成 prompt → stream → 逐字 yield）。独立轻量链路，避免 AgentLoop 的工具注册、上下文管理开销。写入 `token_usage_daily(source='pet_bubble')`。配额判定用 `pet_exp_logs` 同款当日计数（reason=`bubble_llm`，成功生成才记）。

**闲聊（chat）**：走标准 `AgentLoop`，但构造时注入约束：

- `enabled_tools` 过滤为白名单（记忆类），无视 Agent 原配置的工具列表；
- `max_iterations = min(agent.max_iterations, 3)`；
- system_prompt 按 2.3 合成（agent.system_prompt + 宠物人设包装）；

**可见性实时校验**：每次解析绑定 Agent 时检查（a) Agent 存在且 `is_active`；(b) 对当前用户可见（owner 或同租户 tenant 可见）。失败即降级，缓存当次请求内结果。

#### 2.4 降级矩阵

| 场景 | 行为 |
|---|---|
| 未绑定任何 Agent | 本地静态文案（现状） |
| 绑定 Agent 被删除/改私有/停用 | 回退下一级 → 最终静态文案 |
| LLM 调用异常/超时 | 本次回退静态文案，记 warn 日志 |
| 气泡配额超限 | 回退静态文案，hover 提示"今日智能互动已达上限" |
| 全站关闭宠物智能互动 | 全部回退静态文案，绑定配置保留 |
| 宠物接口/LLM 全挂 | 聊天主流程零影响（沿用既有 ErrorBoundary + 附属系统隔离原则） |

#### 2.5 前端设计

- `petStore`：新增 `boundAgent`（解析结果）与 `bubbleStreaming` 状态；气泡文本支持流式累积。
- `PetWidget`：
  - 气泡组件支持打字机效果（流式追加）；3s 无首个 token 直接切静态文案。
  - 右键菜单：「和 TA 聊聊」入口 + 当前人设展示。
  - 新增 `PetChatPanel.tsx`：宠物旁的浮动聊天窗（约 320×400px），复用消息气泡样式组件，位置跟随宠物（锚定逻辑复用 widget 的边距策略）。
- `PetsPage`：宠物卡片加"绑定智能体"选择器；包卡片加"默认人设"设置；闲聊/播报开关。
- 系统配置页：宠物智能互动总开关 + 每日气泡配额配置项。
- 会话列表：`source='pet'` 会话带宠物角标，点击正常进入会话（全屏继续聊）。
